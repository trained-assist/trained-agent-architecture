# Ревью ARCHITECTURE.md v0.6 и связанных документов

## 1. Вердикт

Документ продуманный, внутренне связный и в целом пригодный как *контур* ответственностей, но **не готов как основа для реализации в текущем виде** для команды «1 владелец + агенты». Главная проблема — масштаб: ~20 репозиториев, ~30 идентификаторов, 13 контрактов, 17 инвариантов, 33 work items, 11 итераций до promotion — это описывает платформу уровня 5–10 инженеров, а не автономного владельца. Дополнительно: между документами остались несколько мест, где владелец перехода (escalation, continuation, budget gate, context building) указан неоднозначно; INV-05 (RU/EU) опирается на нерешённый открытый вопрос о резидентности; измеримые критерии приёмки (TTL, budget caps, p95 latency, coverage Ledger) отложены «draft», но без них невозможно закрыть ни одну итерацию. Рекомендую зафиксировать v0.7 с явным «MVP-срезом» (Runner + API + Input/Output + Router + Web, всё остальное опционально) и ужесточить ownership переходов до того, как писать код.

## 2. Сильные стороны

- Разделение Job/Run/Task, трёх jobType и явного `continuationOwner = output | gtd` устраняет классическую путаницу «workflow manager vs recovery».
- Явный запрет «blind retry» внешних мутаций (INV-07, ARCH.111, EXTERNAL-INTEGRATION-GATE.32) — редко встречается в документации такого уровня.
- GTD opt-in с критерием «конкретный следующий шаг» (ARCH.11, PLAYBOOKS.7–9) спасает от превращения каждого cron в workflow-монстра.
- Sandbox Driven Development с обязательным «controlled failure» в каждой итерации (ENGINEERING-APPROACH, IMPLEMENTATION карточки) — сильная дисциплина.
- Разделение «исполнение / доставка» (INV-09, USER-TASK §2) и «state / gtdState» (USER-TASK.73) устраняет классические гонки.
- Отделение «legacy живёт» от «новая реализация параллельно» (ARCH.257–263, IMPLEMENTATION.5–26) — правильная миграционная осторожность.

## 3. Проблемы

### M1 · Критично · Over-engineering масштаба для команды «1 владелец + агенты»
**Где:** ARCH.143–163 (таблица репозиториев), ARCH.113–137 (таблица ID), ARCH.213–227 (A01–A13 + INV-01..17), contracts/README (C01–C13), IMPLEMENTATION.66–79 (I00–I10), 33 work items Z01–Z03/P01–P30.
**Суть:** предложено ~20 репозиториев (из них доменов уже 8), ~30 идентификаторов, 13 контрактов, 17 инвариантов, 11 итераций, отдельные repo для Task Router, Task Queue/Journal/Reporting, GTD Manager, Integration Gate, Error Watcher, Credential Broker, LLM Ladder, Web, TG, Runner, Serverless API adapter.
**Что сломается:** каждая новая граница — это отдельная CI, отдельный деплой, отдельная политика версионирования и отдельная точка отказа. Для одного владельца с агентами основная часть времени уйдёт не в пользовательскую ценность, а в клеевой код и синхронизацию версий между repo. Многие границы будут существовать «на бумаге» дольше, чем проживёт продукт.
**Предложение:** зафиксировать в ARCH отдельный раздел «MVP-срез» (3–5 репозиториев: `ai-agent-runner`, `trained-assist-agent` (новая платформенная часть с Input/Output/Router/Reporting внутри), `trained-assist-web`, `trained-assist-tg-bot`, `trained-agent-architecture`) и явно перенести Integration Gate, Error Watcher, Serverless API, отдельный Task Router, отдельный GTD repo в «stage-2 candidates». В таблице ID оставить обязательными только `userTaskId, runId, jobId, operationId, eventId, artifactId, tenantId/profileId`; остальные вводить только при появлении соответствующей функции.

### M2 · Критично · Неоднозначный владелец «эскалации / budget gate / blocked-состояния»
**Где:** ARCH.67 («для неуправляемой — политика Output/Router»), ARCH.69 («Output создаёт typed continuation»), ARCH.71 («Автоматическая эскалация deterministic → LLM → OpenCode … с bounded attempts/deadline/capacity»), ARCH.71 («Отсутствие бюджета, доступа … требуют соответствующего blocked/reconciliation состояния»), TASK-ROUTER.48 («Router предлагает escalation»), MODEL-GATEWAY.11 («Router выбирает тип, Gateway выбирает provider/model»), MODEL-GATEWAY.15 («Budget policy проверяется до платного вызова»).
**Суть:** в ARCH написано «Output/Router» через слэш, в Router написано «предлагает», в Model Gateway — «проверяет бюджет». Кто фиксирует состояние `blocked: budget_exhausted`, кто выдаёт continuation при `needs_executor`, кто останавливает эскалацию при исчерпании attempts — юридически не определено. Если Router stateless (ARCH.42), он не может учитывать attempts/deadline по задаче; если считает Output — он должен знать policy эскалации; если GTD — но GTD opt-in и для большинства задач отключён.
**Что сломается:** два независимых повтора одной ошибки (INV-02 нарушен на уровне переходов, не только попыток); бюджетный отказ, обработанный как обычная ошибка, приведёт к автоматическому подъёму до агента, что прямо запрещено TASK-ROUTER.11.
**Предложение:** в ARCH заменить «политика Output/Router» на «политика Output» (Router только классифицирует и предлагает); в TASK-ROUTER явно: «Router не создаёт continuation, не изменяет бюджет и не устанавливает blocked — он возвращает `decision + reasonCode`»; в MODEL-GATEWAY явно: «budget gate исполняет Model Gateway, blocked-исход возвращает в Output единым typed outcome». Добавить INV: «одно failed outcome порождает ровно одно следующее действие».

### M3 · Критично · Порядок миграции слишком длинный до первой пользовательской ценности
**Где:** ARCH.190 (порядок вертикальных приёмок), IMPLEMENTATION.66–79 (I00–I10), P12 зависит от P10 и P11 (IMPLEMENTATION.353).
**Суть:** до появления сквозного пользовательского сценария нужно пройти I00 (AutoFix для всех repos), I01 (Runner), I02A (API), I02B (артефакты), I03 (Web + TG + Input/Output). При этом P12 («Primitive Input/Output и routing») заблокирован и на Web, и на Telegram одновременно, хотя в IMPLEMENTATION.34 явно указано «Сначала Web (меньше внешней доставки)».
**Что сломается:** первые месяцы работы не дадут пользователю ни одного полезного действия; при этом I08 (Integration Gate) критичен для HH-рекрутинга — основного продуктового сценария — и отложен до параллельной ветки I05–I07. HH-сценарий де-факто недоступен.
**Предложение:** (1) снять зависимость P12 от P11 — достаточно P10 + минимального Input/Output, TG добавляется как патч; (2) перенести I08 (или его минимальный HH adapter) в общий критический путь сразу после I04, потому что без HH нет текущей продуктовой ценности; (3) в ARCH.190 явно указать «первый пользовательский vertical slice — не позже I03 Web-only».

### M4 · Критично · Отсутствуют измеримые критерии приёмки (TTL, budget caps, latency, coverage)
**Где:** ARCH.255 («TTL в observability и конкретные budget limits ещё draft»), MODEL-GATEWAY.31–35 (5 открытых вопросов, включая budget authority), OBSERVABILITY.87–104 (TTL — «предложение», не production), TASK-ROUTER.148 («Предлагаемые budgets сначала измеряем; hard numbers не обещаем без baseline»), INV-10 («каждый расход привязывается … неизвестная стоимость помечается unknown»).
**Суть:** все числовые пороги отложены. Но приёмка каждой итерации опирается на observability/TTL/бюджет (IMPLEMENTATION карточки, SANDBOX-PLAN.69–95), т.е. «Done требует evidence», evidence требует порогов, порогов нет.
**Что сломается:** невозможно объявить ни одну карточку Done объективно; на практике это выродится в субъективное «вроде работает». INV-10 («каждый расход привязан») невыполним без определения, что считать «каждым» (streaming usage сейчас теряется — см. audits/CODE-BASELINE.49–52).
**Предложение:** зафиксировать хотя бы стартовый numeric baseline прямо в ARCH: TTL error=30d/lifecycle=30d/verbose=7d (как в OBSERVABILITY.93–95) — но со статусом «принято»; p95 time-to-first-useful-reply ≤ N секунд для fast path (ввести placeholder с обязательным замером на I05); target coverage Ledger = 100% provider attempts (включая streaming и retries) — INV-10 дополнить формулировкой «coverage измеряется как доля provider calls со usage-записью, threshold 99%».

### M5 · Важно · INV-05 (RU/EU placement) опирается на нерешённый вопрос о резидентности данных
**Где:** ARCH.233 (INV-05: «Claude/Codex не запускаются в RU»), ARCH.40 («География хранения требует отдельного решения»), ARCH.251 (открытый вопрос: «Где хранятся профили, artifacts и journal для RU/EU и допустимы ли трансграничные snapshots?»), CODE-BASELINE.42–46 («OpenCode как CLI не гарантирует доступность любой выбранной модели из RU»).
**Суть:** инвариант зафиксирован, а контур данных, которые будут передаваться между зонами при EU-run с RU-инструментом, — не зафиксирован. OpenCode в RU, но модель за ним может быть не в RU. Claude в EU, но workspace пользователя — где?
**Что сломается:** при первом же EU-run с российскими персональными данными возникнет либо compliance-инцидент, либо вынужденный откат placement policy. Ревьюер не может проверить INV-05, потому что неизвестно, какие данные считаются «российскими».
**Предложение:** вынести это в блокер до I10 (или раньше) с явным acceptance: «перечень data classes (raw user text, artifacts, credentials, logs, ledger) × допустимые зоны хранения/обработки — утверждён владельцем до запуска EU-run». В INV-05 добавить уточнение «запрет относится к размещению процесса и к фактическому provider endpoint, а не только к worker».

### M6 · Важно · Дыры в durability на стыках «исполнитель принял / очередь удалила»
**Где:** ARCH.63 («После durable acceptance исполнителем запись покидает pending queue»), ARCH.63 («Outbox, идемпотентный приём и lease/watchdog нужны против потери между процессами»), USER-TASK.202–208 («Каждая стадия записывает durable факт до ACK»), contracts/C01.68 («Потеря ACK допускает безопасную повторную доставку»).
**Суть:** протокол «durable acceptance» не формализован. Кто хранит точку приёма — Input или исполнитель? Если у исполнителя своя БД — как избежать split-brain? Сколько watchdog-ов (входной, выходной, GTD, Runner, Watcher) и какой из них авторитетен при конфликте? INV-02 говорит «один авторитетный владелец попытки», но не говорит «один авторитетный владелец задачи».
**Что сломается:** при падении между «исполнитель подтвердил» и «Input удалил» задача может быть одновременно «в работе» и «в очереди», либо потеряться полностью; при двух watchdog-ах возможны двойные ретраи.
**Предложение:** описать явный двухфазный протокол (например: `prepare → lease → commit ACK` с ownerGeneration как в C04.100) в отдельном подразделе ARCH.2 «Durable handoff»; зафиксировать «единственный авторитет для перехода pending → running — Input через lease/ownerGeneration; watchdog только инициирует reconcile, не выполняет сам переход».

### M7 · Важно · Awaiting user input: гонки и durability checkpoint недописаны
**Где:** ARCH.99, PLAYBOOKS §9 (строки 179–203), REVIEW-WITH-REAL-PLAYBOOKS.82 («если observer ждёт сутки, обычный execution timeout нельзя считать timeout всей цели»).
**Суть:** сценарий «ответ пришёл одновременно с restart Runner», «два ответа на одно awaitingInputId», «ответ после timeout одновременно с новым Run» — частично покрыт (PLAYBOOKS.198: «Повтор submit ответа возвращает прежний receipt»), но не покрыт явный протокол checkpoint/restore для движков, которые не умеют resume (само признано в ARCH.99: «Не предполагается, что каждый engine уже поддерживает универсальное восстановление»). Если движок не умеет — что видит пользователь и что происходит с уже запущенными побочными эффектами шага?
**Что сломается:** восстановление после ответа может выполнить шаг дважды (нарушение INV-07 при наличии внешних мутаций); либо задача навсегда уйдёт в `blocked` без понятного пути.
**Предложение:** в ARCH.99 явно: «движок без поддерживаемого checkpoint → задача получает `needs_replay_from_last_committed_step`, а не `resume`; конкретный шаг исполняется заново с dedup по operationId». В acceptance P23/P24 добавить fixture «ответ пришёл во время рестарта Runner».

### M8 · Важно · Отдельные repo для Integration Gate, Error Watcher, Serverless API — преждевременны
**Где:** ARCH.105 («Решение: отдельный репозиторий» для Gate), ARCH.160 (Error Watcher «отдельный подключаемый repo выбран»), ARCH.184, SERVERLESS-AGENT-API.57.
**Суть:** для команды «1 владелец + агенты» три дополнительных сервиса с собственным deployment, ключами и observability — это заметный оверхед. Error Watcher с LLM-диагностикой — это ещё и непрерывный расход токенов. Serverless Agent API — внешний продукт, у которого в текущем документе не назван ни один клиент.
**Что сломается:** три дополнительные CI/CD, три набора секретов, три точки отказа. Error Watcher без пользователей будет либо тишиной, либо шумом.
**Предложение:** Gate сделать модулем внутри `trained-assist-agent` с явным публичным интерфейсом (по C10) и вынести в отдельный repo только когда появится второй потребитель или второй провайдер с независимым lifecycle. Error Watcher отложить до стабилизации Observability contract; Serverless API — до появления внешнего клиента, сейчас ограничиться внутренним Task API.

### M9 · Важно · Термин «Orchestrator» продолжает жить в contracts/README
**Где:** contracts/README.6–8 («Слово Orchestrator ниже — историческое …»), но далее строки 52–60, 63, 74, 84, 92, 104, 126, 136 продолжают использовать «Orchestrator владеет …».
**Суть:** формально «историческое обозначение» оговорено, но таблицы C01–C09 физически ссылаются на несуществующий компонент. Для читателя-исполнителя это провоцирует «всё-таки нужен Orchestrator».
**Что сломается:** при реализации C01–C04 непонятно, кто исполняет «Orchestrator-обязанности» — Input, Task Router, Output, GTD или отдельный control plane.
**Предложение:** в contracts/README провести механическую замену: C01 «Input Task Queue Manager», C02 «Output + Journal», C03 «Input/Reporting + Runner», C04 «Task Router → Runner», C09 «GTD Manager»; отдельно оставить подстрочник «Orchestrator — упразднён».

### M10 · Важно · Security: известные пробелы T0 не имеют плана закрытия в целевой модели
**Где:** CODE-BASELINE.20–25 («Codex и cwd вне профиля оставляют только allowlist/bridge, без run-as»), CODE-BASELINE.26–30 («Постоянный профиль сейчас является рабочей директорией … `.agent-home` сохраняется между запусками»), CODE-BASELINE.58–62 («Без `CRED_ENCRYPTION_KEY` store пишет plaintext»), ARCH.201 (таблица «Изоляция … Проверяемый lifecycle clean room без скрытых исключений»), INV-06.
**Суть:** в ARCH декларируется «без скрытых исключений» и fail-closed изоляция, но ни в ARCH, ни в IMPLEMENTATION нет карточки, которая бы явно закрывала три конкретных пробела из CODE-BASELINE: (а) исключение Codex/cwd из run-as, (б) отсутствие эфемерного HOME, (в) plaintext credentials без ключа. При этом эти пробелы прямо противоречат INV-06.
**Что сломается:** при миграции пользовательских профилей на новый Runner либо унаследуем plaintext-credentials и постоянный `.agent-home`, либо будем «вдруг» выяснять, что Codex не работает в чистом clean room.
**Предложение:** завести явный эпик «Закрыть legacy gaps isolation» с тремя acceptance: (1) каждый engine либо работает в run-as без исключений, либо задекларирован как unsupported в clean room; (2) `GCS_WORKSPACE_SYNC` либо реализован, либо удалён из mode bits; (3) `CRED_ENCRYPTION_KEY` обязателен — без него startup fail-closed. Привязать к I01 или вынести в блокер до I02A.

### M11 · Важно · Capability Catalog (4 режима) и два LLM-этапа — преждевременный eval
**Где:** CAPABILITY-CATALOG §1 (4 supportedModes), CAPABILITY-CATALOG.34–36 (сравнение one-call vs two-stage на sanitized corpus), IMPLEMENTATION.471–518 (I06 с P19–P21).
**Суть:** для одного владельца с агентами строить версионированный каталог с brief tier-1/tier-2, scoped cache key из 4 компонент и сравнивать два LLM-пайплайна на labelled corpus — это работа исследовательской группы. Корпус нужно размечать, за ним нужен review, метрики нужно трактовать.
**Что сломается:** I06 не будет закрыт объективно; либо eval выродится в «на глаз».
**Предложение:** оставить в каталоге только `supportedModes` (без tier-1/tier-2 brief) и один универсальный путь reply-or-route. Сравнение one-call vs two-call отложить до момента, когда на production накопится ≥ 500 реальных запросов с разметкой от владельца.

### M12 · Важно · Контекст-билдер: владелец не определён
**Где:** TASK-ROUTER.111–122 («Context builder — bounded host function: retrieval выполняется до recipe либо по одному явному recipe outcome»), ARCH.42 («Router stateless … получает её необходимую проекцию во входе»), TASK-ROUTER.160–164 («Router … context/ в минимальной структуре repo»).
**Суть:** если Router stateless и context builder «bounded host function», то кто конкретно вызывает builder — Input при подготовке? Router перед dispatch? Отдельный модуль? Если context builder внутри Router repo, то Router уже не stateless (кэш, контекстные версии).
**Что сломается:** при росте нагрузки один и тот же контекст будет готовиться дважды (Input и Router), либо Router станет скрытым stateful-сервисом и начнёт конфликтовать с Task Journal.
**Предложение:** явно в ARCH: «Context builder принадлежит Input/preparation; Router получает готовый `RoutingContext` и не строит его». В TASK-ROUTER.160 убрать `context/` из минимальной структуры repo Router.

### M13 · Важно · Reconciliation внешних мутаций без верхнего срока
**Где:** ARCH.111, EXTERNAL-INTEGRATION-GATE.32 («Timeout мутации требует reconciliation»), INV-07, contracts/C06.116 («При unknown effect сперва reconciliation; при невозможности доказать outcome — needs_review»).
**Суть:** состояние `outcome unknown` может висеть неограниченно долго, если провайдер молчит или reconciliation невозможен. Ни в одном документе не задан SLA: через сколько `unknown` эскалируется в `needs_review` / `failed` / «требуется ручное действие».
**Что сломается:** задачи будут зависать в неопределённом статусе; Reporting (USER-TASK §9) не сможет показать пользователю честный ответ; при этом повторная отправка запрещена, т.е. пользователь заблокирован.
**Предложение:** в EXTERNAL-INTEGRATION-GATE добавить: «`unknown` без подтверждённого reconciliation в течение N часов переводится в `needs_review` с адресованным действием оператору; политика — per-provider конфиг». Привязать acceptance к P25.

### M14 · Мелочь · Диаграмма ARCH §1 вводит в заблуждение стрелкой `C → S`
**Где:** ARCH.32 (`C --> S`), ARCH.40 (пояснение «Reporting доступен через авторизованный API»).
**Суть:** пояснение есть, но стрелка визуально подразумевает прямой доступ пользователя к Storage.
**Что сломается:** при реализации Web-слоя возникнет соблазн отдать клиенту API Reporting напрямую в обход авторизации по scope.
**Предложение:** заменить стрелку на `C -->|"AuthZ API"| S` или убрать, заменив на `C --> G`.

### M15 · Мелочь · Разное написание `gtdId`-семантики между документами
**Где:** ARCH.118 («gtdId | Контроль одной задачи; сохраняется при продолжениях и в истории»), PLAYBOOKS.121 («В этой версии один gtdId связан с одной userTaskId»), REVIEW-WITH-REAL-PLAYBOOKS.60 («GTD может контролировать U1 без P1»), ARCH.97 («самостоятельная дочерняя задача получает свой userTaskId … собственный gtdId — лишь при необходимости контроля»).
**Суть:** формулировки совместимы, но не идентичны: REVIEW допускает `gtdId` без playbook, ARCH-таблица подразумевает это лишь в расширении. Мелочь, но провоцирует вопросы при имплементации.
**Предложение:** в ARCH.118 расширить: «gtdId существует и без planId/playbookRef».
