## 1. Границы плана

Этот план — **ближний контур**: он чинит действующий сервис (trained-assist-tg-bot + trained-assist-agent + привязка trained-assist-web), потому что «выпиливание скрытой блокировки» — большая задача и идёт одним из шагов общего рефакторинга взаимодействия, который нужен живому сервису сейчас.

Он **не отменяет и не дублирует** I03 из [плана реализации](IMPLEMENTATION-AND-INTEGRATION-PLAN.md) (новый sandbox gateway на новом API): целевая модель (сценарий RC) общая для обоих путей; I03 строит новый gateway с нуля в песочнице, этот план — правки действующего кода, каждая из которых проходит обычный PR-flow со своим CI. Как пути сольются при pilot/cutover — отдельное решение по разделу «Путь интеграции» там же.

Правило владельца из IMPLEMENTATION §«Решение владельца»: изменения действующих репозиториев — отдельные implementation actions после review. **Этот документ и есть то, что выносится на review;** имплементация фаз начинается только после апрува.

### 2.1 «Скрытый запрет» — это две независимые блокировки

**Блокировка A — lane-очередь ядра** (`trained-assist-agent/src/core/admission.js:3-23`):
- scope `lane:<conversationKey>` = endpoint+chat+topic: ≤1 интерактивный ран в диалоге, «even across different sessions»;
- scope `session:<profile>:<sessionId>` — один писатель истории (все каналы, включая web);
- вторая задача **не отклоняется**: `POST /run` всегда отвечает `202`, а `src/runner/index.js:1223-1224` ставит её в очередь со статусом «↪️ Ожидаю завершения предыдущей работы. В этом диалоге выполняю задачи по очереди. Начну автоматически; повторно отправлять не нужно.» и после освобождения лейна запускает сама;
- норматив: `docs/architecture/channel-execution-concurrency.md`, сценарии CH-01…CH-11.

**Блокировка B — `busy` накопителя шлюза** (`trained-assist-tg-bot/src/intake-buffer.js`, Durable Object на чат):
- busy держится весь прогон (с #280), снимается `POST /internal/run-finished` от агента (`src/gateway-callback.js:75`) либо self-heal-опросом `GET /tasks/running?chatId=` (агент `src/handlers/api.js:139-150`), либо таймером `BUSY_MAX_MS`;
- во время busy новый ввод копится: квитанция `heldText` (строка 103) «✓ Получил ещё N сообщений, пока идёт задача. «▶️ Запустить агента» — запущу их сразу после неё.»;
- тап «▶️» во время busy → `/flush` ставит `launchQueued` → ответ `queuedText` (строка 104) «⏳ Порция из N сообщений уйдёт агенту сразу после текущей задачи…» + кнопка «↩️ Отменить передачу агенту» (`CANCEL_BTN:100`); повторный тап — `src/handlers/callbacks.js:637` «⏳ Идёт текущая задача. Запущу эти сообщения сразу после неё — жать ещё раз не нужно…»;
- модель может прочитать накопленное прямо в ходе (`GET /held:437` → MCP `get_new_messages`, `src/mcp-skills/tools/02-chat-history.js:165`, `src/live-inbox.js`).

Таким образом юзерский выбор нигде не спрашивается: либо молчаливая очередь (A), либо молчаливое отложение с кнопкой, которая сама решает «запущу после» (B). Ответы на нажатия вида «ожидает/запущу после» на устаревших кнопках — прямое следствие (см. аудит, находки A-4, A-5).

### 2.2 Кнопки и статусы: где живут

| Элемент | Место |
|---|---|
| «▶️ Запустить агента» + «📋 Посмотреть input» | шлюз `intake-buffer.js:82-83` (`LAUNCH_BTN`) |
| «↩️ Отменить передачу агенту» | `intake-buffer.js:100` (`CANCEL_BTN`) |
| «📋 Посмотреть input» вместо ▶️ под статусами «задача принята» | `intake-buffer.js:91` (`STATUS_BTN`, #297/#303) |
| «⛔ Стоп» / «➕ Дополнить» на прогресс-сообщении | агент `src/runner/claude-runner.js:57-62` (`runningControls`, `input_run\|`, `journal`, `stop\|`, `sup\|`) |
| Живой inbox и «потреблённые» сообщения | `GET /held`, `consumed` в run-finished |
| Диагностика состояния чата | `GET /debug/intake/:chatId` (шлюз `src/index.js:130`) |

### 2.3 Что уже есть и не переписывается заново

Накопитель с коллектором и тишина-гейтом (US-BUF-01/03/04), busy на весь прогон + run-finished + self-heal, live inbox, отмена тапа (`intake_cancel`), per-message markup-clear (`intake-buffer.js:325`), scoped stop (`/tasks/stop` с chatId), `controlKey` для кнопок, pre-queue quick intents (US-QUEUE-03), спека Core 02 (SS-01…SS-14) с принятым планом PR. Всё это — основа, не объект выпиливания.

## 3. Три вопроса владельца и решения (сессия 30.09.2026)

| # | Вопрос | Решение |
|---|---|---|
| 1 | Что значит «запустить новую задачу», когда ран уже идёт? | **Обе кнопки: «В очередь» и «Параллельно»** — скрытый запрет снимается, становится явным выбором |
| 2 | Смысл «добавится к выходу старой»? | Работает коряво: **кнопку «➕ Дополнить» на сообщении старой задачи убрать**; при новом вводе во время накопления давать кнопку **«🛑 Стоп и запуск с добавкой»** |
| 3 | Баг «кнопка горит где-то, нажатие говорит, что-то ожидает»? | Подтверждён. Общее правило: **кнопки максимально дропать, оставлять только на сообщениях с контекстом и предлагаемыми шагами** |

Все три зафиксированы в [сценарии RC](scenarios/interaction/run-conflict-explicit-choice.md) (§2, §3, RC-07). Дополнение того же дня: опция «Пока подождать» в меню снята как лишняя дублирующая — ждущее состояние даёт бездействие юзера, а не кнопка (RC §2 п. 5, RC-06).

### Ф1 — кнопочная гигиена (самый дешёвый, заметный сразу)
- При показе новой квитанции/пикера/статуса снимать markup у предыдущих неактуальных сообщений того же чата (паттерн уже есть: `intake-buffer.js:325` — переносится на project/session-пикеры и устаревшие коллекторы).
- Убрать кнопки со статусов, которые не предлагают действия (правило владельца п. 3 из §3).
- Закрывает находку аудита A-5 и класс KNOWN-BUGS US-BUG-01 (находку A-4 закрывает Ф3 — там тап становится явным выбором).

### Ф2 — честный Стоп и supplement (без этого стоп-опции меню нельзя показывать)
- Реализация уже распланирована в [Core 02, §5](https://github.com/trained-assist/trained-agent-architecture/blob/dc50e7f4b0c001c15acd68497f06673922b25db6/scenarios/sources/trained-assist-agent/docs/user-scenarios/core/02-stop-and-supplement.md) (SS-13 сделан; SS-06/09/10 частично в шлюзе; тумбстоун/kill/`POST /tasks/supplement` — нет). Здесь фаза лишь привязывает эти PR к нашему плану и фиксирует связку: **стоп-опции меню включаются только после приёмки Ф2** (ОВ-4 сценария).
- «Стоп гасит и очередь» (US-MISC-05) входит в Ф2 как SS-05.

### Ф3 — меню явного выбора
- Шлюз: на held/коллектор busy показывать меню §3 сценария; `/flush` по тапу → показ меню, а не молчаливый `launchQueued`; пункт «В очередь» = текущий `launchQueued` (механизм остаётся, но выбор явный); «↩️ Отменить» работает на любой пункт.
- Агент: `/run` получает явный параметр запуска (`queue`/`parallel`/`stop+…`); без параметра поведение не меняется (совместимость с API и вебом до Ф4/Ф5).
- Тишина-гейт (авто-запуск по 3 минутам) в busy отключается — в idle остаётся (US-BUF-04/RC-06).
- Убирается `sup|` из `runningControls` (`claude-runner.js:62`) — замена приходит из Ф3-меню (решение владельца №2).

### Ф4 — снятие скрытого запрета («Параллельно»)
- admission: обход **только lane-scope** по явному флагу и только для запуска в отдельной сессии; session-scope никогда (CH-05 структурно защищён).
- Рендер: у каждого рана своё прогресс-сообщение и свой набор кнопок (уже так: `controlKey` на цепочку) — проверить, что статусы не перетирают чужие сообщения при двух активных.
- Документы: ревизия INV-03 в ARCHITECTURE v0.6 (новая формулировка — в сценарии RC §5), правка CH-01/US-QUEUE-01 в Core 01/CURRENT-STATE, согласование с PR #1 (ОВ-3).
- Риск: два потока статусов в одном чате. Митигация: независимые сообщения + явное имя задачи в статусе; если при ревью решим, что потоки всё же путаются, — «Параллельно» под вопросом (ОВ-3).

### Ф5 — привязка веба
- Веб уже параллелен по сессиям; работа здесь — привести **конфликтные состояния** к той же модели: `409 duplicate` из `handlers/web.js` превращается в видимое «задача идёт, запуск встал в очередь» (семантика RC-02), stop/supplement из веба — та же C03-адресация.
- CH-05: вторая вкладка на одну сессию → видимое ожидание второго писателя (сейчас защиты нет, запланирована в PR2 эпика #1365).

### Ф6 — зачистка
- Выпилить заменённые тексты/флаги/пути (см. таблицу фаз), обновить `docs/INTAKE-SCENARIO-MATRIX.md`, `docs/user-stories/*` в исходных репозиториях и их копии в `scenarios/sources/` (осознанно, с обновлением IMPORT-MANIFEST) — статусы юзер-стори с этого момента ведутся здесь, по правилам из аудита §4.

## 6. Открытые вопросы и риски

1. **Параллельность против читаемости чата** — главный риск Ф4; держим как гипотезу до латч-тестов и ревью владельца (ОВ-3 сценария, пересечение с PR #1 US-06).
2. **Порядок Ф2 → Ф3**: показывать меню со стоп-опциями до готовности честного Стопа нельзя — иначе возвращается класс R1–R6 Core 02.
3. **Согласованность источников**: после Ф6 sources-снапшот и runtime readers (GOALS.md и др.) обновляются отдельной осознанной операцией — копирование не мигрирует readers ([scenarios/README](scenarios/README.md)).
4. **Не задеть зелёное поле**: ни одна фаза не меняет поведение, которое I03 собирает заново в песочнице; при pilot/cutover эти правки становятся reference-контрактами для нового gateway.
5. **Статус фаз после 02.10.2026:** C01/C02/C03 приняты ([контракты](contracts/README.md), приложение A), поэтому Ф1–Ф6 — **reference-контракты ближнего контура**, а не отдельная вселенная: по одной семантике с C01/C02/C03, спорное не выбирается молча. Каждая фаза идёт по трём корзинам ([исследование границы шлюза](research/GATEWAY-BOUNDARY-RESEARCH-2026-10-02.md) §3 L4): дефект прода заводится в репозитории, где он живёт ([tg-bot #325](https://github.com/trained-assist/trained-assist-tg-bot/issues/325) — стоп не гасит outbox/retry, [#326](https://github.com/trained-assist/trained-assist-tg-bot/issues/326) — стоп/статус/файлы уходят на другой VM из-за выбора исполнителя в шлюзе, [#231](https://github.com/trained-assist/trained-assist-tg-bot/issues/231) — durable приём webhook); уже принятая семантика не переформулируется, а цитируется (INV-03/INV-08, C03); пробел — карточка здесь.
