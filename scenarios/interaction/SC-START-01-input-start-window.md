# SC-START-01 — Приём ввода и отложенный старт

**Статус:** target — предложенное целевое поведение; issue на реализацию открыт.  
**Issue метода:** [Communication Skills #36](https://github.com/trained-assist/trained-assist-communication-skills/issues/36). **Issue интеграции:** [architecture #170](https://github.com/trained-assist/trained-agent-architecture/issues/170).  
**Область:** Telegram, Web и API; канал-независимое решение о маршруте, channel-specific подтверждение.

## Ценность для пользователя

Пользователь может отправить запрос несколькими сообщениями. Система сразу подтверждает, что она поняла и когда начнёт. Пользователь успевает дополнить ввод; при явном «продолжай» ожидание короче. Стартовый проход не тратит ресурсы на предварительное исследование: он либо начинает с простых уточняющих вопросов, либо обрабатывает уже однозначное продолжение.

## Условия

- Новое входное сообщение принято шлюзом и связано с правильной conversation/task.
- До dispatch система может объединять сообщения одного ожидающего окна.
- Классификатор первичного маршрута не зависит от основной модели и не создаёт Agent Run.

## Основной поток

1. Gateway надёжно принимает сообщение и передаёт его с conversation identity, request/event ID и порядком.
2. До ответа исполнителя control plane вызывает stateless MCP method `check_task_clarity` из Communication Skills с накопленным input bundle и необходимым диалоговым контекстом. Метод немедленно классифицирует ввод и может использовать shared classification ladder; он не вызывает execution model, research или инструменты:
   - `explicit_continue`: пользователь недвусмысленно просит продолжить/подтверждает предложенное продолжение;
   - `understood_request`: запрос понятен, явного немедленного продолжения нет;
   - `needs_user_detail`: даже полезное уточнение пока нельзя сформулировать без одного конкретного недостающего факта;
   - `cancel`: пользователь просит остановиться/отменить ожидающую работу.
3. Решение классификатора, generation/version окна ожидания, буфер входа и deadline сохраняются надёжно и согласованно. Повтор одного входного event ID не создаёт повторное сообщение/окно.
4. Gateway отправляет подтверждение, соответствующее сохранённому решению.
5. До deadline каждый новый содержательный ввод добавляется в буфер, увеличивает generation, аннулирует старый таймер и немедленно приводит к новой классификации.
6. По действующему deadline scheduler/host проверяет generation, состояние и отсутствие более нового ввода. Один владелец атомарно переводит окно в dispatched и запускает нужный путь ровно один раз.
7. Pending окно и deadline переживают рестарт; доставка и запуск остаются идемпотентными.

## Классификация и реплики

| Результат до запуска | Реплика в канале | Ожидание и следующий путь |
|---|---|---|
| `understood_request` | «Понял запрос. Если вы ничего не добавите, через 3 минуты начну и вернусь с уточняющими вопросами». | 180 секунд тишины после последнего содержательного сообщения. Затем минимальный сценарий уточнения: сформулировать только нужные вопросы. |
| `explicit_continue` | «Понял, продолжаю. Подожду 20 секунд на случай дополнения, затем начну». | 20 секунд тишины после последнего содержательного сообщения. Затем продолжить текущую задачу с накопленным контекстом. |
| `needs_user_detail` | «Чтобы начать, уточните, пожалуйста: <один конкретный недостающий факт>». | Не выдавать ложное обещание «начну, если будет понятно». До получения факта ничего не запускать; после ответа классифицировать объединённый ввод заново. |
| `cancel` | Коротко подтвердить отмену, если есть активное ожидающее окно. | Атомарно инвалидировать окно/deadline; будущие stale callbacks ничего не запускают. |

`check_task_clarity` различает явное продолжение и простое новое содержательное дополнение. Если после явного «продолжай» пришло дополнительное сообщение, оно объединяется с вводом и классифицируется заново; если последнее сообщение само не является явным продолжением, применяется 180 секунд. Повторное подтверждение «продолжай» оставляет 20 секунд. Реализация должна определить контролируемый словарь/правило явных фраз и проверять его на неоднозначных/отрицательных примерах.

## Telegram: controls до готовности input

На стартовом состоянии нового/независимого ввода, пока input bundle ещё собирается и не считается готовым для просмотра, Telegram показывает ровно четыре действия в таком порядке:

1. «Изучи и задай вопросы»
2. «Дай полный ответ»
3. «На твоё усмотрение»
4. «Очистить весь ввод»

Кнопка «Посмотреть input» на этом состоянии не показывается: просматривать ещё неготовый input преждевременно, а дополнительная кнопка перегружает стартовый выбор. Это не отменяет capability просмотра input в более поздних состояниях, где bundle уже сформирован и сценарий разрешает просмотр.

Implementation: [trained-assist-tg-bot #397](https://github.com/trained-assist/trained-assist-tg-bot/issues/397). Scenario-change coordination: [architecture #187](https://github.com/trained-assist/trained-agent-architecture/issues/187).

## Запуск

- Для `understood_request` стартовый сценарий по умолчанию — минимальное уточнение цели/недостающих требований. Он не выполняет research, web search, MCP discovery, чтение больших файлов или другие подготовительные действия заранее.
- Для `explicit_continue` исполнение продолжает заявленную пользователем работу. Существующая политика безопасности/approval и ограничения каналов остаются обязательными.
- Таймер — это только окно сбора ввода, не сигнал, что запрос может стать понятным в будущем.
- До dispatch не запускаются execution model, Agent Run или предварительный research. Сам `check_task_clarity` может вызвать shared classification ladder; стоимость этой оценки измеряется отдельно. Подтверждение, сохранение окна и изменение deadline принадлежат control plane.

## Состояния окна (логические)

`collecting` → `scheduled` → `dispatched` → завершение обычным task lifecycle.  
Из `collecting`/`scheduled` возможен переход в `cancelled`. Новое сообщение в `scheduled` создаёт новую generation того же окна либо атомарно заменяет предыдущее окно; точная storage mapping — в Task Store контракте/реализации. Stale callback не меняет состояние. Терминальные состояния нельзя воскресить повторной доставкой.

## Канальные различия

Одинаковы классификация, семантика буфера, deadlines и ровно-один dispatch. Текстовые подтверждения Telegram/Web могут различаться в пределах таблицы. Для API эквивалентом подтверждения является немедленный response/event с классифицированным состоянием и ожидаемым deadline. Если API контракт не поддерживает такую семантику, реализация должна явно описать совместимое представление до изменения клиента.

## Ошибки и гонки

- **Повтор/переупорядочение доставки:** dedupe по event/request ID; сохранять зафиксированный порядок; не терять средние сообщения.
- **Рестарт:** восстановить последнее поколение окна и вычислить остаток времени по durable deadline, не перезапуская исходные 180/20 секунд с нуля.
- **Новое сообщение одновременно с deadline:** транзакционно победит либо append+generation bump, либо единственный dispatch; старый timer не может стартовать устаревший buffer.
- **Повторный/просроченный callback:** проверить generation, status и idempotency key; no-op для устаревшего.
- **Отмена одновременно с timer:** ровно один переход выигрывает атомарно; если dispatch уже зафиксирован, честно сообщить, что запуск уже начался, и применить штатный stop к задаче.
- **Сбой доставки ack:** сохранённое окно не теряется. Retry доставки не должен повторно планировать старт.
- **Сбой scheduler:** durable reconciliation находит просроченные scheduled окна и запускает их идемпотентно.
- **Ошибка `check_task_clarity`:** timeout, ladder/provider failure, malformed output или stale revision — best-effort failure. Не преобразовывать ошибку в решение. Атомарно не менять уже сохранённый decision, buffer, generation или deadline; не отправлять ack/уточнение на основании отсутствующего результата; не запускать execution agent/research и не отменять ранее валидно поставленное ожидание. Не делать retry loop. Для нового ввода без успешной классификации сохранить существующее legacy/default поведение (если найдено), иначе оставить событие ожидающим и использовать нейтральную техническую реплику без обещания запуска. Записать только безопасный код/IDs, без сырого пользовательского текста.

## Acceptance evidence для реализации

Communication Skills issue #36 владеет контрактом и реализацией метода. Architecture issue #170 владеет интеграцией, runtime статусом и сквозным чек-листом. Реализация должна приложить ссылки на владельцев и PR-ы, pinned source revision, sanitized transcript, временные метки/измеренные задержки, task/window/generation IDs, events/logs, результаты тестов и controlled failures. Минимум: 180s, 20s, message bump/reset, неоднозначная фраза, cancel, restart, duplicate timer/event и гонка timer/new input. Проверка отсутствия pre-deadline Agent Run/основного LLM должна быть инструментальной, не только утверждением.
