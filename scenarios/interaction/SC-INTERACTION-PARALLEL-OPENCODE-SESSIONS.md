# SC-INTERACTION-PARALLEL-OPENCODE-SESSIONS — Параллельные дочерние сессии opencode внутри одного запуска

**Статус:** proposed; architecture change (in progress). Связанный эпик: trained-assist/ai-agent-runner (parallel opencode sessions). Mock-сценарий: `mother-and-kids:*` в `ai-agent-runner` (`MockTestWorker`).

## Актор и цель

Пользователь даёт задачу, которую агент может разбить на независимые части (research по статьям, анализ нескольких репозиториев, параллельные проверки). Цель — получить итоговый ответ быстрее за счёт параллельного выполнения дочерних сессий opencode, при этом не потерять ни одного сообщения и не сломать доставку.

## Предусловия

- Запуск (`run`) уже принят Runner API и имеет родительскую сессию opencode.
- Родитель имеет право спавнить дочерние сессии (ограничение по числу и бюджету).
- Все сессии (родитель + дети) работают внутри одного запуска/изоляции и пишут в общий event log рана.
- Каждое сообщение помечено адресатом: `user` (финальный ответ пользователю) или `parent` (репорт родителю) или `child:<id>` (адресовано конкретному ребёнку).

## Основной поток

1. Пользователь отправляет задачу с признаком распараллеливания (или агент сам решает разбить).
2. Родительская сессия opencode анализирует задачу и спавнит N (3–5) дочерних сессий, передавая каждой подзадачу.
3. Дочерние сессии выполняются параллельно, каждая пишет прогресс/результат.
4. Дочерняя сессия, завершив подзадачу, отправляет репорт родителю (`parent`).
5. Родитель собирает репорты, синтезирует итоговый ответ и отправляет его пользователю (`user`).
6. Runner API доставляет финальный ответ пользователю через стандартный канал (Telegram/outbox).

## Маршрутизация сообщений

- Сообщение с адресатом `user` → доставляется пользователю (финальный ответ или промежуточный статус, если явно помечен).
- Сообщение с адресатом `parent` → доставляется родительской сессии (репорт/результат ребёнка).
- Сообщение с адресатом `child:<id>` → доставляется указанному ребёнку.
- Сообщение без адресата или с неизвестным адресатом → логируется как предупреждение, не доставляется молча.

## Отказы и восстановление

- **Родитель умер до детей:** дети продолжают работу; при воскрешении родителя (resume) он получает накопленные репорты и завершает синтез. Дети не перезапускаются.
- **Один ребёнок умер:** родитель фиксирует потерю, может перезапустить подзадачу или продолжить с частичным результатом (явно в итоговом ответе).
- **Все дети умерли:** родитель завершает с ошибкой/частичным ответом, не зависает.
- **Родитель умер и не воскрес:** запуск завершается ошибкой; доставляется сообщение об ошибке пользователю.
- **Дубликат репорта (ребёнок повторил):** дедупликация по idempotency key ребёнка.

## Граница доказательства

PASS этого сценария доказывает маршрутизацию сообщений между родителем/детьми/пользователем, сборку результатов, восстановление родителя и устойчивость к смерти участников. Это **не** доказывает реальный spawn opencode (покрывается отдельно `opencode-adapter` и живыми E2E).

## Приёмка

- Mock-сценарии `mother-and-kids:all-good`, `:mother-dead-before-kids`, `:one-child-dead`, `:all-dead` проходят через `MockTestWorker` и возвращают контрактные статусы/логи.
- Сообщения с адресатом `user` доставляются пользователю; с адресатом `parent` — родителю.
- При смерти родителя дети не теряются; воскрешённый родитель получает репорты.
- Итоговый ответ пользователю корректен при частичной потере детей.

## Отдельные follow-up границы

Реальный spawn opencode, ограничения по числу детей, бюджет, изоляция между детьми, дедупликация репортов и доставка через Telegram/outbox — отдельные задачи (см. эпик в ai-agent-runner).
