# Telegram first-release acceptance — 06.10.2026

Статус: **acceptance draft** для переноса Telegram UX на новый Router/Control Plane/Runner. Это сценарии и проверяемые инварианты, не утверждение, что новый runtime уже их проходит.

Источники UX baseline: [legacy Telegram user stories](../sources/trained-assist-tg-bot/docs/user-stories/CURRENT-STATE.md), [явный выбор при конфликте задач](run-conflict-explicit-choice.md), [Router/MCP contract](../../TASK-ROUTER-AND-MCP.md), [текущий критический путь](../../IMPLEMENTATION-AND-INTEGRATION-PLAN.md#актуальная-приёмка-и-критический-путь--04102026). Переносить поведение и обученные UX решения, но не legacy ownership/runner implementation.

## Общие условия приёмки

- Для каждого входа Router сначала фиксирует один результат из разрешённого intent/capability списка; только затем вызывает выбранный MCP method или принимает решение о Agent Run. Нет молчаливого fallback на Agent Run при неизвестном intent или недоступной capability.
- Quick answer и host-owned form/choice не создают Agent Run. Каждый принятый Agent Run имеет один `userTaskId`, один актуальный `runId` и устойчивые event/status IDs после retry/restart.
- «Принято», «запускаю», «работает» показываются только при соответствующем durable переходе и рядом с этой задачей. Состояние редактируется в связанном task message/receipt; не создаются несвязанные статусные сообщения.
- Накопленный ввод хранится в исходном порядке, не теряется при debounce, callback повторе, рестарте процесса или временной недоступности Runner. Автоматический запуск/действие во время активного Run не подменяет явный выбор пользователя.
- Кнопки адресуются конкретным snapshot/task/run. Повторный callback идемпотентен; устаревшая кнопка не действует на новую задачу.
- Для STOP/restart отсутствие точного Runner exit proof означает hold: никакой replacement/continuation, пока terminal state не подтверждён. GHA workflow cancellation само по себе не является доказательством выхода процесса.
- Stop/cancel state всегда адресуется точными `userTaskId`/`runId`/generation, никогда только Telegram chat/conversation. Неизвестный исход старой задачи запрещает только её повтор/continuation и действия, явно зависящие от её результата; независимая новая задача и новый input snapshot не ждут её terminal state.
- `/stop` в idle очищает только текущий незапущенный intake snapshot и оставляет канал готовым к следующему сообщению. Stop выполняющейся задачи — task-scoped cancel; подтверждённая остановка завершает эту задачу. Неопределённый Runner исход остаётся честно `unknown`, но не является блокировкой всего чата и не даёт права на автоматический повтор той же задачи.
- Media intake — отдельная граница хранения, не диспетчер запуска: сначала подтверждённая durable запись байтов и manifest, затем admission. Ошибка загрузки/хранения отвечает «Не удалось принять файл»; исходное сообщение не создаёт task/run, не вызывает classifier/Runner и не теряет уже сохранённый ввод других задач.

## Сценарии

| ID | Ввод и состояние | Видимое поведение | Проверяемое состояние / эффект |
|---|---|---|---|
| TG-01 Fast answer | Пользователь задаёт вопрос, fixture классифицирует его как быстрый ответ. | Бот отвечает непосредственно в контексте запроса; не пишет «Задача принята». | Классификация записана до ответа; `userTaskId`/`runId` отсутствуют; `runnerSubmitCount=0`; ответ доставлен один раз. |
| TG-02 MCP method | Запрос однозначно выбирает разрешённую capability и fixture method. | Бот показывает короткий progress только если вызов реально принят; результат отвечает на исходное сообщение. | `intent_classified` раньше `mcp_invoked`; вызван ровно один method с ожидаемыми typed args; trace содержит имя метода/версию каталога; `runnerSubmitCount` соответствует политике этого метода (0, если Agent Run не предусмотрен). Ошибка/несовпадение версии fail-closed. |
| TG-03 Agent task | Запрос требует работы агента; classifier явно выбирает Agent Run. | Одно подтверждение запуска, затем статус этой же задачи и итог/файл. | Admission предшествует сообщению «принято»; один `userTaskId`, один `runId`; итоговый artifact скачивается и совпадает по manifest/hash; delivery deduplicated. |
| TG-04 Burst / accumulation | В idle пользователь быстро отправляет три текстовые реплики, затем выбирает запуск; повторяет callback. | Одна квитанция показывает накопление и понятное действие; составной текст содержит все три реплики в исходном порядке. | Один immutable input snapshot; один classifier decision; максимум один Agent Run; повторная кнопка не создаёт новую admission. Таймер и force-word покрываются тем же snapshot contract. |
| TG-05 Input while busy / queue | Run A работает; пользователь посылает несколько сообщений B и явно выбирает «В очередь». | Receipt прямо говорит, что B идёт после A; B не изображается уже работающим. | A и B имеют разные task/run IDs; все B inputs удержаны; B стартует ровно один раз после terminal A; если A потерял связь, B не стартует автоматически. |
| TG-06 Stop and add/restart | Run A работает; B накоплен; пользователь выбирает stop/add или stop/new. | Задача B запускается только согласно выбранной связи: «после A» ждёт именно A; независимая «новая задача» не ждёт. Если A отменена, статус A меняется отдельно и честно. | STOP snapshot стабилен; stop evidence применяется только к точным task/run/profile/generation. При `pending`/`unknown` нельзя повторить или продолжить A и нельзя заявлять, что A остановлена; при этом независимый task ID не блокируется status A. Queue-after/continuation ссылается на конкретный A и ждёт его результат. Повтор callback не создаёт дубль. |
| TG-06a Stop/reset idle intake | В чате есть только незапущенный текст/файлы; пользователь отправляет `/stop`, затем обычный новый запрос. | Старый накопленный ввод явно очищен; следующий запрос принимается сразу как новый. | Сброшен только unlaunched snapshot; нет task/run/admission для очищенного ввода; новый request получает новый snapshot/request/task ID и принимается ровно один раз. Повтор `/stop` безопасен и не меняет следующую задачу. |
| TG-06b Failed/unknown task isolation | Task A завершилась `failed` или имеет честный `unknown`; пользователь отправляет независимую задачу B в том же Telegram-чате. | B проходит обычный UX и создаётся сразу; бот не просит ждать/подтверждать stop A и не сообщает, что A остановлена, если исход неизвестен. | A и B имеют разные `userTaskId`; нет чатовго mutex и неявной зависимости. `unknown` сохраняет запрет auto-rerun/continuation A, но не блокирует admission B. Только явный dependency на A может ждать её результата; проверяется по task ID между разными чатами/диалогами тоже. |
| TG-07 Awaiting choice/form | Агент запрашивает typed выбор/форму; пользователь отвечает через host handler. | Форма привязана к нужной задаче, ответ виден в её контексте. | Проверены input type/schema/ownership; answer сохраняется как continuation event; новый Agent Run не стартует, если контракт не требует continuation. Повтор submit идемпотентен. |
| TG-08 Stale/duplicate controls | Пользователь повторно нажимает старую Start/Stop/Cancel кнопку после смены состояния; посылает одинаковый callback дважды. | Честный короткий ответ «действие уже выполнено/квитанция устарела»; кнопка снимается. | Старый callback не меняет новую задачу; side-effect count не увеличивается; один snapshot и один transition. |
| TG-09 Restart / result replay | Worker/API/Telegram delivery прерывается после admission или результата; сервис перезапускается. | Бот восстанавливает корректный статус и доставляет прежний результат без фальшивого нового «работает». | Повторное чтение/replay использует те же IDs; второй submit не возникает; task result/artifact остаётся доступен; unresolved execution не превращается в автоматический rerun. |
| TG-10 Clear all accumulated input | Пользователь набрал несколько сообщений/файлов, возможно уже переносил их в retry/failed draft, но ни один snapshot ещё не принят CP. | Рядом с запуском доступно «🧹 Очистить весь ввод»; после нажатия видно, что все блоки очищены и новый ввод начнётся с чистого листа. | Атомарно очищаются все unlaunched `buf`, `retryBatch` и failed draft records текущего владельца; закрывается их pending-batch учёт; нет task/admission/run и side effects. Не трогаются accepted/launching tasks, чужой chat/profile, native stop evidence и результаты. Если media ещё загружается или admission неизвестен, операция fail-closed: сообщает о конфликте и сохраняет всё, повторный/устаревший callback безопасен. |
| TG-11 Work style at launch ([#159](https://github.com/trained-assist/trained-agent-architecture/issues/159)) | Пользователь собрал текст/ссылки/файлы в существующем draft и выбирает один из трёх способов: «Изучи и задай вопросы» (`explore`), «Дай полный ответ» (`answer`) или «На твоё усмотрение» (`auto`). | Кнопки находятся на карточке накопленного контекста и сами запускают выбранный режим; не требуется второй выбор/кнопка запуска. Ответ соответствует цели исходного запроса, а не расширяет её. | До выбора нет запуска. Выбор атомарно фиксирует полный упорядоченный snapshot, typed `workStyle` и revision и создаёт одну admission/task; prompt builder включает ровно один соответствующий style block. `explore` задаёт до трёх существенных вопросов и переходит в task-scoped Awaiting; ответ пользователя продолжает ту же задачу и может сменить следующий шаг. `answer` даёт полный ответ/заказанный артефакт, но не выполняет лишь предложенные действия. `auto` выбирает достаточный шаг, не означает безграничное автономное выполнение. Проверить повтор/stale/конкурирующие callbacks, вложения, restart и append во время запуска: один immutable snapshot/workStyle, без потери позднего ввода и без повторного запуска. |
| TG-12 Text + audio accumulation | Пользователь отправляет текст, затем аудио и ещё текст, пока задача не запущена; затем нажимает «Запустить». | До запуска бот только подтверждает приём и тип аудио, не отвечает на его содержание и не утверждает, что аудио расшифровано. После запуска задача получает текст в исходном порядке и исходный аудиофайл. | Байты аудио загружены в долговременное хранилище; batch содержит только текст, порядок, тип/метаданные и устойчивую ссылку с размером и checksum. CP связывает ссылку с `userTaskId`, Runner материализует байты в input workspace. `file_id`, поддельная ссылка или недоступный артефакт не проходят admission/start; ошибка загрузки видна, неполный batch не отправляется. Проверить повторы webhook, рестарт между загрузкой и запуском, checksum/size, отсутствие байтов в KV/logs, отсутствие Agent Run до явного запуска и ровно один Run после него. |
| TG-13 Media persistence failure | Telegram прислал файл; intake storage (download, object put или manifest commit) возвращает ошибку/timeout/неполную запись. | Одно понятное сообщение «Не удалось принять файл. Попробуйте ещё раз»; бот не запускает работу и не утверждает, что файл принят. | Доказать все три границы: Intake не создаёт usable ref при неполном put; CP не принимает task с отсутствующим/непроверенным manifest; Runner submit count остаётся 0. Нет частичного batch admission, dangling ref не доходит до classifier/агента; повтор webhook идемпотентен, успешная повторная загрузка создаёт ровно один attachment/task после явного запуска. Буфер никогда не вызывает CP admission или Runner сам. |

### Stop, task state и media intake: обязательная матрица

| Вариант | Состояние конкретной задачи | Независимая новая задача | Повтор/продолжение этой задачи |
|---|---|---|---|
| `/stop` при незапущенном intake | Intake snapshot очищен; run отсутствует | Принимается немедленно | Не применимо |
| Runner definitive 4xx до admission | Attempt завершён как `failed/runner_rejected`; не `unknown` | Принимается немедленно | Только явный новый пользовательский запуск после исправления причины |
| Runner timeout/connection loss после dispatch | `unknown`; прежний attempt остаётся reconciliation-only | Принимается независимо, без chat lock | Нельзя слепо пересоздать; только тот же idempotency key/reconciliation либо явное подтверждённое решение |
| Task A → B с явной зависимостью | A остаётся источником контекста | B может быть создана, но соответствующий execution ждёт результат A | Связь хранится как `dependsOnUserTaskId=A`, не как chat busy flag |
| Ошибка media durable storage до admission | Файл отклонён; usable manifest отсутствует | Текст/другой независимый ввод не затрагивается | Файл можно загрузить повторно идемпотентно; admission только после успешной записи |

## Уровни проверки

1. **CI/offline:** настоящий Router, conversation/intake state machine и handlers; синтетический classifier, stateful MCP facade и disposable Task Store; запрещённый Runner stub со счётчиком вызовов. Для TG-06/06a/06b/13 обязательно проверять task-scoped IDs, возможность admission независимого task после failure/unknown, явную dependency edge, порядок событий, пользовательский receipt, state diff, media durable-commit boundary и нулевые side-effect counts на отказе.
2. **Sandbox integration:** тот же контракт через Telegram test Worker, CP/D1/Workflow, test MCP host и настоящий Runner. Проверять только настроенные capability bindings; записать deploy SHA/Worker versions, `userTaskId`, `runId`, snapshot ID, event sequence и artifact hashes.
3. **Production canary:** один разрешённый пользователь/бот после полного sandbox acceptance; отдельные критерии rollback и запрет автоматического переноса активных legacy tasks. Sandbox PASS не считается production PASS.

## Не входит в первый gate

Видео и импорт старых профилей не следует объявлять принятыми только потому, что текстовый путь прошёл. Фото и аудио проходят отдельный TG-12 acceptance gate; типизация, приватные данные и права проверяются отдельными сценариями с legacy fixtures. Перенос UX не даёт права ослаблять авторизацию, profile isolation или Runner stop gate.
