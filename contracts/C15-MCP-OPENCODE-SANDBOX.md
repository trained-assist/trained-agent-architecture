# C15 — MCP в OpenCode: sandbox, пользователи, ролевой доступ

Status: scenario draft · 2026-10-11. Это черновик сценария для Epic #253. Runtime-реализация следует только после принятия этого контракта.

## Акторы и границы

| Актор | Граница |
|-------|---------|
| OpenCode (IDE/agent) | Подключается к нашему sandbox remote MCP server |
| Пользователь (ручное создание) | Имеет персональный ключ, роль, статус |
| Sandbox MCP server | Проверяет ключ, роль, выдаёт/запрещает инструмент |
| Ladder (LLM) | Совместимый OpenAI endpoint, независим от MCP auth |

## Сценарий A: ручной пользователь → персональный ключ → MCP tool call

**Участник:** Оператор (admin) создаёт пользователя вручную через Account CLI или sandbox ops-команду.

**Вход:**
- Пользователь: stable ID, normalized email, name, role (например `recruiter`)
- Ключ: персональный API key, выдаваемый пользователю, хранится как hash
- Роль: определяет набор доступных MCP tools

**Поток:**
1. Оператор создаёт пользователя с ролью `recruiter`.
2. Система выдаёт персональный ключ (показывается один раз).
3. OpenCode пользователя подключается к sandbox MCP server с этим ключом.
4. MCP server проверяет ключ → находит пользователя → проверяет роль.
5. Пользователь вызывает разрешённый tool (например `agent-runs.create`) через нативный MCP tool call.
6. Tool выполняется, результат наблюдаем (nonce, run ID, status).

**Ожидаемый результат:**
- Разрешённый tool: успешный вызов, наблюдаемый результат.
- Запрещённый tool (другой роли): denial с ясной причиной.
- Отозванный ключ: denial при следующем запросе.
- Disabled user: denial при следующем запросе.

**Негативные проверки:**
- Ключ не существует → 401/403.
- Ключ отозван → 401/403.
- Пользователь disabled → 401/403.
- Роль не имеет доступа к tool → 403.
- Прямой вызов другого пользователя (cross-role) → denied.

## Сценарий B: тот же user/key в Ladder

**Участник:** Пользователь с тем же ключом использует Ladder (OpenAI-compatible endpoint).

**Вход:** Тот же персональный ключ.

**Ожидаемый результат:**
- Список пользователей, права, лимиты, учёт, ACL — доступны по роли.
- Ключ валиден для Ladder и MCP одновременно (общая identity).

## Сценарий C: сайт с самостоятельной регистрацией

**Участник:** Новый пользователь регистрируется на сайте самостоятельно.

**Вход:** Email, пароль, имя.

**Ожидаемый результат:**
- Пользователь создан с ролью по умолчанию.
- Ключ выдан после подтверждения (email verification).
- Та же identity работает в MCP и Ladder.

## Сценарий D: OAuth follow-up (отложен)

OAuth-интеграция — отдельный follow-up после принятия A–C.

## Требования к реализации

1. **Human role и identity — серверные.** Каждый data-bearing handler проверяет ACL.
2. **Одинаковые IDs разных сессий изолированы.** User/key привязаны к конкретной сессии.
3. **Machine catalog/digest отдельно.** Discovery/invocation contract для машинных клиентов.
4. **Нет gateway-token admin fallback.** Каждый запрос аутентифицируется по ключу пользователя.
5. **Account CLI и web используют общие functions.** Одна реализация проверки ключа/роли.
6. **Тесты проверяют наблюдаемый контракт и негативные случаи.**
