# Connected App identity and profile authority

Status: target decision for C14; implementation and live acceptance are tracked separately. [Connected-app identity v1](https://github.com/trained-assist/trained-assist-control-plane/pull/66) is the current read-token contract. This document describes the missing authority and three different callers: browser, agent relay and background worker.

## Authority

The existing platform authentication boundary must provide a verified, stable `principalId` through a trusted server-side session resolver. A platform-owned identity/profile service (initially a Control Plane module) stores membership, the selected profile for each user session, grants, session generation and revocation. Membership provisioning needs an explicit owner and audited source; the resolver cannot accept a browser or model-provided profile ID as proof. A future OIDC identity provider may authenticate the principal, but adding a new login provider is not a prerequisite of this contract. The old Agent web JWT, Runner API-key registry and Control Plane task-admission principal are not this authority.

`principalId`, `profileId`, user-session ID, app audience, scopes and generation are separate fields. A browser profile switch increments that browser session's generation and invalidates its app tokens; it does not retarget an already admitted task or disable a durable schedule. Logout revokes the browser session. Membership loss, disabled principal or relevant grant removal blocks **new effects** for every affected caller class; any effect already dispatched with an unknown outcome requires reconciliation. The application additionally checks that the requested vacancy/catalog/deal belongs to the grant's profile. Agent Run ID is correlation data only.

## Browser handoff

CRM Web and Recruiting Web act as confidential Backend for Frontend (BFF) clients. The platform authorization component offers an Authorization Code flow with PKCE `S256`, transaction-bound `state`, registered client identity and exact redirect URI. The single-use, short-lived code is bound to the authenticated platform session, selected profile generation, client, audience, redirect URI and PKCE challenge. Its atomic exchange checks all bindings and current membership. The BFF stores app tokens server side and gives the browser only a secure, HttpOnly, SameSite session cookie; it never places an access token in a URL, JavaScript state or local storage. The BFF performs API calls with the audience-bound app token. This follows [RFC 10017 §6.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1) and [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1).

An app token is opaque, short lived and scoped to one app/profile. The app's registered service credential calls Control Plane introspection on protected requests and receives the [v1 active response](https://github.com/trained-assist/trained-assist-control-plane/pull/66) only while session, selected profile, membership, audience and scopes still match. The default is no authorization cache; if a bounded cache is later needed, its maximum stale-revocation window must be explicit and accepted separately. An introspection outage returns a typed unavailable result and permits no protected read or side effect; it is not evidence of logout or lost membership. Browser profile IDs and old cookies are never issuance inputs.

The BFF validates Origin/CSRF tokens for commands, rotates its session handle after code exchange, uses only registered server-owned return destinations and allowlisted outbound backends, and keeps codes, tokens and service credentials out of logs. Its cookie authenticates the browser session but does not replace domain-object authorization. A deep link is resolved to a permitted app object after handoff; a wrong-profile object is denied. These controls complement the [RFC 10017 CSRF and cookie guidance](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1.3.3).

## Agent relay and schedules

The agent's MCP relay obtains a separate platform-issued delegation bound to the **originating task's** trusted principal and profile, target app and requested capability. A later browser profile switch does not change that task's profile. Before each new effect, the app checks current membership/grant status and applies the same domain handler and ownership rules as its UI. The model cannot author `principalId`, `profileId`, audience or scope; run/task IDs correlate work but confer no access. A relay credential is never borrowed from the browser cookie.

Recruiting schedules use an app-owned service identity and a durable grant bound to the owner profile, vacancy, schedule ID and allowed search/score commands. Each occurrence has an idempotency key and audit receipt. The service rechecks current membership/grant, vacancy ownership, schedule enablement and credential status before dispatch. Browser expiry, logout or profile switch does not silently disable a legitimate schedule; explicit grant/membership revocation blocks future occurrences. Unknown outcomes are reconciled, never blindly replayed. This workload grant is separate from the v1 human browser token and from HH's provider OAuth credential.

## Legacy identity migration

Preserve old `USER_ID`/username as source identifiers. An owner-reviewed, receipt-bound crosswalk must explicitly attest `old namespace + source key → principalId + profileId` using both frozen source evidence and current platform membership. Missing, conflicting or unowned rows remain quarantined. No pathname, display name, email similarity or Runner key entry is sufficient by itself. Only approved bindings authorize real catalog/notes/candidate imports; source revision and object ownership are checked independently.

## Independent acceptance gates

- **Shared identity:** establish the trusted existing-platform user-session resolver, audited membership provisioning and selected-profile lifecycle. With two users/profiles, deny forged profile input, stale generation, cross-audience grants, replay, logout and removed membership. The v1 contract in each consumer must remain byte-pinned or be explicitly versioned.
- **Each browser app:** prove its own BFF code/PKCE callback, server-side token session, command CSRF, safe return target, introspection availability behavior, domain authorization and route parity. An app can remain offline while the other is accepted.
- **Agent relay:** bind delegation to the originating task profile; prove a browser switch does not retarget it, while grant revocation prevents new effects. Only declared agent-exposed operations need MCP transport parity. Direct UI/API paths prove zero Agent Run launches.
- **HH schedule and GCP exit:** use a separate durable service grant and verify a full required schedule cycle on a verified non-GCP target. RU is a candidate where approved; CRM readiness is not a gate. See [HH #187](https://github.com/trained-assist/trained-assist-hh-skill/issues/187).
- **CRM legacy import:** approve the old-user crosswalk privately and receipt-bind data, then accept catalog/deal journeys and Weeek effects under CRM's own gate. This does not delay an independently accepted HH exit.
