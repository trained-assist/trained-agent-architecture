# Connected App identity and profile authority

Status: target decision for C14; implementation and live acceptance are tracked separately. Authority ownership is tracked in [architecture issue #173](https://github.com/trained-assist/trained-agent-architecture/issues/173). [Connected-app identity v1](https://github.com/trained-assist/trained-assist-control-plane/pull/66) is the current read-token contract. This document describes the missing authority and three different callers: browser, agent relay and background worker.

## Authority

**The Agent profile authority is the source of truth for the authenticated Agent user, that user's membership in profiles, and the profile selected for the current Agent/browser session.** It must be a stable server-side identity/profile API owned with the Agent platform, not a value inferred by an application, model, Runner key, task-admission principal, or profile directory. The current legacy Agent web JWT and `web_current` cookie do not satisfy this contract by themselves: they identify a legacy profile login and do not prove an independently authenticated human-to-profile membership. Until the Agent exposes and verifies this authority, Connected App user issuance remains disabled.

The Control Plane remains the Connected App authorization broker and token issuer. It owns registered app clients, app-specific grants/scopes, one-use authorization codes, app-session generations/revocation, and introspection. It does not create or independently edit the canonical Agent user-to-profile membership or selected profile. Before issuing a code/token, it obtains a current, authenticated Agent profile assertion bound to the Agent session, principal, selected profile and profile generation; that assertion is audience/client-bound, short-lived and replay-protected. The Control Plane may keep a derived authorization projection, but every issue/refresh/introspection decision must honor Agent revocation and profile-generation changes within an explicitly accepted bound. If Agent authority cannot be reached or verified, issuance and protected access fail closed.

The Agent assertion is a versioned server-to-server contract, not a browser payload or a model tool argument. Its minimum claims are `issuer`, stable `principalId`, `profileId`, `agentSessionId`, `profileGeneration`, registered `clientId`/audience, exact redirect URI, transaction nonce, unique assertion ID, issue time and expiry. It is signed by an Agent-owned key whose public key and rotation policy are registered with CP. CP validates signature, issuer, time, client/audience and redirect, then atomically consumes the nonce/assertion ID. The Agent derives principal and selected profile from its authenticated session; it never accepts those claims from query parameters or request bodies. App-specific scopes remain CP grants and are not asserted by the browser or model. The exact wire schema and signing algorithm are versioned by the Agent contract and pinned by CP and app consumer tests.

Profile membership is provisioned and reviewed in the Agent authority from an explicit, audited source. Existing mappings require owner attestation and a private receipt; names, emails, chat IDs, pathnames, the current profile cookie, and old usernames alone are not sufficient evidence. A future OIDC provider may authenticate the person, but the canonical profile catalog, membership and selection remain Agent-owned.

`principalId`, `profileId`, user-session ID, app audience, scopes and generation are separate fields. A browser profile switch increments that browser session's generation and invalidates its app tokens; it does not retarget or automatically cancel an already admitted task, and does not disable a durable schedule. An admitted task remains bound to its originating profile; each subsequent app effect is authorized against current membership and grants. Logout revokes the browser session. Membership loss, disabled principal or relevant grant removal blocks **new effects** for every affected caller class; any effect already dispatched with an unknown outcome requires reconciliation. The application additionally checks that the requested vacancy/catalog/deal belongs to the grant's profile. Agent Run ID is correlation data only.

## Browser handoff

CRM Web and Recruiting Web act as confidential Backend for Frontend (BFF) clients. The browser starts an Authorization Code flow with PKCE `S256` at the Agent-owned identity/profile authority, using transaction-bound `state`, registered client identity and exact redirect URI. The Agent authenticates the user and resolves the selected profile from its server-side session. The Control Plane redeems the Agent-issued, single-use, short-lived authorization assertion and creates an app code bound to the verified Agent session, principal, selected profile generation, app client, audience, redirect URI and PKCE challenge. Atomic exchange checks all bindings, current Agent membership/selection and the current app grant. The BFF stores app tokens server side and gives the browser only a secure, HttpOnly, SameSite session cookie; it never places an access token in a URL, JavaScript state or local storage. The BFF performs API calls with the audience-bound app token. This follows [RFC 10017 §6.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1) and [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1).

An app token is opaque, short lived and scoped to one app/profile. The app's registered service credential calls Control Plane introspection on protected requests and receives the [v1 active response](https://github.com/trained-assist/trained-assist-control-plane/pull/66) only while the Agent session, selected profile generation and membership, and the Control Plane app grant, audience and scopes still match. The default is no authorization cache. If a bounded Agent-revocation projection is needed for availability, its maximum stale-revocation window and outage behavior must be explicitly accepted; an unbounded or undocumented cache is not allowed. An introspection outage returns a typed unavailable result and permits no protected read or side effect; it is not evidence of logout or lost membership. Browser profile IDs and old cookies are never issuance inputs.

The BFF validates Origin/CSRF tokens for commands, rotates its session handle after code exchange, uses only registered server-owned return destinations and allowlisted outbound backends, and keeps codes, tokens and service credentials out of logs. Its cookie authenticates the browser session but does not replace domain-object authorization. A deep link is resolved to a permitted app object after handoff; a wrong-profile object is denied. These controls complement the [RFC 10017 CSRF and cookie guidance](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1.3.3).

## Agent relay and schedules

The Agent's MCP relay obtains a separate Control Plane delegation using the **originating task's** server-stamped Agent principal/profile context and Agent profile generation, bound to the target app and requested capability. The model cannot author these fields. A later browser profile switch does not change that task's profile. Before each new effect, the app checks current Agent membership/generation and Control Plane grant status, then applies the same domain handler and ownership rules as its UI. Run/task IDs correlate work but confer no access. A relay credential is never borrowed from the browser cookie.

Recruiting schedules use an app-owned service identity and a durable grant bound to the Agent-owned owner profile, vacancy, schedule ID and allowed search/score commands. Each occurrence has an idempotency key and audit receipt. The service rechecks current Agent profile ownership/generation and Control Plane workload grant, vacancy ownership, schedule enablement and credential status before dispatch. Browser expiry, logout or profile switch does not silently disable a legitimate schedule; explicit Agent membership or workload-grant revocation blocks future occurrences. Unknown outcomes are reconciled, never blindly replayed. This workload grant is separate from the v1 human browser token and from HH's provider OAuth credential.

## Legacy identity migration

Preserve old `USER_ID`/username as source identifiers. An owner-reviewed, receipt-bound crosswalk must explicitly attest `old namespace + source key → Agent principalId + profileId` using frozen source evidence and current Agent membership. Missing, conflicting or unowned rows remain quarantined. No pathname, display name, email similarity, chat ID or Runner key entry is sufficient by itself. Only approved bindings authorize real catalog/notes/candidate imports; source revision and object ownership are checked independently.

## Independent acceptance gates

- **Shared identity:** implement the Agent-owned authenticated principal/profile API, audited membership provisioning and selected-profile lifecycle, then connect the Control Plane broker to its signed, audience-bound assertions and revocation/generation checks. With two users/profiles, deny forged profile input, stale generation, cross-audience grants, replay, logout, unavailable Agent authority and removed membership. The Agent assertion contract, CP token contract and each app domain contract are versioned independently; consumers pin each applicable version.
- **Each browser app:** prove its own BFF code/PKCE callback, server-side token session, command CSRF, safe return target, introspection availability behavior, domain authorization and route parity. An app can remain offline while the other is accepted.
- **Agent relay:** bind delegation to the originating task profile; prove a browser switch does not retarget it, while grant revocation prevents new effects. Only declared agent-exposed operations need MCP transport parity. Direct UI/API paths prove zero Agent Run launches.
- **HH schedule and GCP exit:** use a separate durable service grant and verify a full required schedule cycle on a verified non-GCP target. RU is a candidate where approved; CRM readiness is not a gate. See [HH #187](https://github.com/trained-assist/trained-assist-hh-skill/issues/187).
- **CRM legacy import:** approve the old-user crosswalk privately and receipt-bind data, then accept catalog/deal journeys and Weeek effects under CRM's own gate. This does not delay an independently accepted HH exit.

The [Control Plane runtime candidate #68](https://github.com/trained-assist/trained-assist-control-plane/pull/68) and [authorization-code candidate #70](https://github.com/trained-assist/trained-assist-control-plane/pull/70) are disabled by default; [#69](https://github.com/trained-assist/trained-assist-control-plane/pull/69) records the missing trusted user/profile resolver. They need an Agent-owned authority adapter before they can issue real user sessions. None is a live login. CRM [#30](https://github.com/flexi-consulting/crm-web/pull/30) and Recruiting [#70](https://github.com/trained-assist/trained-assist-recruiting-web/pull/70) consume the v1 read contract behind opt-in boundaries.
