# Ревью ARCHITECTURE.md v0.6 от Claude

## 1. Вердикт в трёх фразах

Разделение ответственности описано хорошо, но у архитектуры нет опоры: не выбрано хранилище, в котором живёт состояние задачи. Все слова «durable», «outbox», «lease» и «fencing» в документе держатся именно на этом решении. Кроме того, самый частый сценарий сегодняшнего продукта почти не описан: это разговорная сессия, где человек пишет «а теперь сделай так» и ждёт, что агент помнит контекст. Документ хорошо проектирует фоновые задачи, но обходит главный путь пользователя. Прежде чем писать код, нужно закрыть три вопроса: хранилище состояния, строить ли движок надёжного исполнения самим или взять готовый, и модель разговорной сессии. Остальное уже можно уточнять по ходу работы.

## 2. Что хорошо (коротко)

- Задача пользователя (userTaskId) отделена от попытки (runId) и от сессии движка. INV-01 и INV-02 прямо запрещают старую путаницу, когда задачей считалась сессия чата.
- «Исполнено» и «доставлено» — разные статусы (INV-09, ARCH.73). Это правильно: сбой Telegram не должен повторять работу агента.
- GTD по умолчанию выключен (ARCH.11). Решение зрелое: не каждое расписание превращается в процесс с контролем результата.
- Запрещён слепой повтор внешнего действия с неизвестным исходом (INV-07, ARCH.111).
- Новая система строится параллельно, живой прод не трогаем (ARCH.259). Для команды без запасного инженера это верная осторожность. Цену такого подхода разбираю в C5.

## 3. Замечания

### C1 · Критично · Не выбрано хранилище, в котором живёт состояние задачи

**Где:** ARCH.42 («Очереди, результаты, доставка и GTD имеют собственное durable state»), ARCH.63, ARCH.139. [CODE-BASELINE](audits/CODE-BASELINE.md) в разделе «Локальное single-owner» прямо пишет: «Конкретный storage и механизм ещё не выбраны. Общий object bucket нельзя считать межмашинным transactional task store».
**Суть:** «durable» встречается почти в каждом абзаце. Но ни один документ не говорит, где это состояние физически хранится и какая транзакционная гарантия у него есть. У Input, Output, GTD, Journal и delivery записано «собственное durable state», то есть пять хранилищ. Переходы между ними склеиваются через outbox/inbox. Для команды из одного человека это пять мест, где можно разойтись.
**Что сломается:** контракты C01–C04 нельзя реализовать и проверить без конкретной транзакционной модели. «Удалить из pending только после ACK» и «отвергнуть результат старого владельца по поколению» — это свойства одной транзакции в одной базе. Если их размазать по пяти хранилищам, придётся строить распределённый протокол. Именно в нём и появятся те дыры, о которых пишет MiMo в M6.
**Предложение:** сначала принять решение-опору, а контракты писать после него.
1. **Одна транзакционная база** для задач, попыток, переходов, outbox и ожиданий. Input, Output, GTD и Journal становятся логическими таблицами и модулями в ней, а не отдельными хранилищами. Удаление из очереди, смена статуса и запись события делаются одной транзакцией, поэтому двухфазный протокол из M6 MiMo становится не нужен.
2. Конкретный выбор, от простого к сложному: одна Postgres на control plane; Cloudflare D1 или Durable Objects, если control plane живёт рядом со шлюзом (шлюз, web и ladder уже на Cloudflare); SQLite на одной VM как первый шаг с явным ограничением «одна VM — один владелец».
3. Статус задачи хранить **таблицей состояния плюс журналом событий**, а не вычислять из событий (ARCH.73 «статус вычисляется из durable событий» — это event sourcing, для одного владельца он дорог в сопровождении). Журнал нужен для истории и replay, а текущий статус — это колонка.

### C2 · Критично · Движок надёжного исполнения проектируется с нуля, хотя готовые решения не рассматривались

**Где:** ARCH.63–67 (outbox, идемпотентный приём, lease/watchdog), ARCH.99 (ожидание ответа без polling, checkpoint, возобновление новым Run), ARCH.97 (дедупликация повторного запуска расписания), contracts C04 (lease, fencing generation), C11 (GTD inbox/outbox). Temporal упомянут один раз, в [PLAYBOOKS-VS-GTD](PLAYBOOKS-VS-GETTING-THINGS-DONE-BOUNDARIES.md) стр. 58, и только как ориентир для терминов.
**Суть:** сумма требований — долговечные шаги, таймеры, ожидание внешнего события неограниченное время без расхода ресурсов, идемпотентные шаги, повтор с дедупликацией и один владелец перехода. Это точное описание durable workflow engine. Такие продукты существуют и решают ровно эту задачу: Temporal, Restate, DBOS, Inngest, Cloudflare Workflows с `waitForEvent` и `sleep`. В core уже работает свой механизм долгих планов: шаг может уснуть до ответа пользователя и проснуться по событию (task_item_wait/wake, gtd-controller, durable-recovery). Сейчас этим пользуются несколько живых планов. В ARCH.202 он описан одной строкой «существуют cron и контроль в core».
**Что сломается:** на самописный движок с lease, fencing, reconciliation таймеров и replay уйдёт большая часть бюджета итераций I01–I07. Результат будет хуже готового, а сопровождать его будет один человек.
**Предложение:** до I01 провести короткое сравнение трёх вариантов, по одной странице на каждый:
(а) взять внешний движок: Cloudflare Workflows лучше всего вписывается в текущую инфраструктуру, а Restate или DBOS — если control plane будет на VM с Postgres;
(б) развивать уже работающий механизм планов из core, выделив его в новый репозиторий по контракту;
(в) писать с нуля, как сейчас подразумевает документ.
Критерии: ожидание ответа без расхода ресурсов, дедупликация шагов, fencing, наблюдаемость, цена сопровождения одним человеком. Вариант (в) допустим только если (а) и (б) проиграют по записанным причинам. Если выбрать (а), документ заметно упростится: Input, Output, GTD inbox и awaiting input станут примитивами движка, а не отдельными компонентами.

### C3 · Критично · Разговорная сессия, основной путь пользователя, не спроектирована

**Где:** ARCH.129 (conversationId/sessionId: «не владелец задачи»), ARCH.69 (follow-up как «typed continuation той же задачи»), ARCH.170 (snapshot → run → export), INV-03. В contracts C05 сказано: «доступ к native resume должен быть отдельной runtime-state policy», и решение не принято.
**Суть:** сегодня пользователь в основном ведёт долгий диалог. Он пишет, агент отвечает, пользователь уточняет или просит «а теперь сделай так же, но…». Агент продолжает работу с полным контекстом, потому что сессия движка возобновляется. В целевой модели нет ответов на три вопроса:
1. Следующая реплика в диалоге — это новая задача (новый userTaskId) или продолжение прежней? Как понять, к какой из нескольких открытых задач она относится?
2. Откуда агент в чистой среде (clean room) получает контекст прошлых ходов? Можно сохранять состояние сессии движка как артефакт между запусками, а можно пересобирать контекст из журнала. От этого выбора зависят цена каждого хода, задержка и качество ответа.
3. Нужно ли каждую реплику активного диалога пропускать через reply-or-route (ARCH.69)? Если да, то каждый ход получает лишний вызов модели и риск, что второй классификатор отправит продолжение диалога не туда.
**Что сломается:** новая система будет хороша для фоновых задач, но на ежедневном сценарии окажется хуже старой: агент «забывает», ответы медленнее, иногда уходят не в тот исполнитель. Тогда cutover не состоится, и старая система останется навсегда (см. C5).
**Предложение:** добавить в ARCH отдельный раздел «Разговорная сессия» с решениями:
- реплика в активном диалоге **закрепляется** за текущим исполнителем и сессией без повторной классификации, пока пользователь явно не сменит тему или проект;
- состояние сессии движка — это отдельный класс данных (runtime state) со своим владельцем, сроком хранения и регионом. Clean room материализует его при старте и экспортирует при завершении, так же как рабочие файлы;
- userTaskId создаётся на каждую содержательную просьбу, conversationId связывает их в диалог. Reporting показывает обе проекции.
Критерий приёмки: сценарий «пять последовательных уточнений в одном диалоге после рестарта runner между 3-м и 4-м» проходит без потери контекста. Рядом нужно записать замер задержки и стоимости хода относительно текущего прода.

### C4 · Важно · Не назначен владелец проекта (профиль → проект → сессия)

**Где:** projectId встречается только в таблице ID (ARCH.128) и в INV-04. Раздел «Одна задача» (ARCH.44–73) не говорит, кто определяет проект входящего сообщения.
**Суть:** владелец продукта называет структуру «профиль → проект → сессия» важнее сиюминутного удобства. В core уже есть логика выбора проекта для новой сессии: один проект — выбираем его, нет проектов — создаём, несколько — спрашиваем. В целевой схеме этот шаг никому не принадлежит. Gateway «не выбирает исполнителя», Router «stateless», а выбор проекта требует состояния (список проектов, последний активный) и иногда вопроса пользователю.
**Что сломается:** выбор проекта снова размажется по шлюзу, Router и агенту. Одна и та же реплика в Web и в Telegram попадёт в разные проекты. Вопрос «в каком проекте?» станет таким же источником «Неизвестной команды», как было с /persona.
**Предложение:** явно записать, что проект определяется на этапе Input (подготовка задачи) до Router. Ответ «нужно спросить» — это законный исход: задача переходит в Awaiting user input. Router получает уже определённый projectId. Добавить инвариант: «у каждой принятой задачи определён проект, либо она ждёт выбора проекта».

### C5 · Важно · У параллельной системы нет условий завершения, и цель движется

**Где:** ARCH.259–261 («Старые репозитории/production не заменяются и не удаляются этой работой», «Legacy cleanup/archive не входят в текущий план»), ARCH.247.
**Суть:** идея строить параллельно правильная, но у неё нет условий выхода. Одновременно старый прод продолжает получать фичи: проекты, плейбуки, ApplyLink, генерацию ТЗ, расписание (эпик #1489 открыт прямо сейчас). Каждая такая фича увеличивает объём, который новая система должна догнать до cutover.
**Что сломается:** одновременно живут две системы, баги чинятся дважды, cutover откладывается, потому что старая система всё время умеет больше. Показательный пример: расписание в проде сейчас недоступно и переделывается (#1489), а в новом плане оно стоит последним, в I07. Одна и та же фича проектируется дважды с разной архитектурой.
**Предложение:**
1. Ввести правило: новая крупная фича старого прода проектируется сразу на контрактах новой архитектуры (C01–C04). В старом ядре допустим только тонкий адаптер. Первым кандидатом сделать расписание (#1489): вместо двух реализаций получится одна.
2. Для каждой когорты записать условие cutover (какие сценарии проходят, какая задержка и стоимость) и дату, после которой старый путь для неё выключается.
3. Legacy cleanup не обязательно планировать, но нужен критерий «старый путь больше не принимает новые задачи этой когорты». Без него «параллельно» превращается в «навсегда».

### C6 · Важно · Для флагманского сценария не описан путь к Claude Code

**Где:** ARCH.71 («Автоматическая эскалация deterministic → LLM → OpenCode», «Лестница OpenCode → Claude Code/Codex не рассматривается»), [TASK-ROUTER](TASK-ROUTER-AND-MCP.md) стр. 7 («Явный пользовательский запуск другого engine…»), INV-05.
**Суть:** автоматический путь заканчивается на OpenCode, Claude Code и Codex запускаются только по явной просьбе пользователя. Но сегодня глубокие сессии («▶️ Запустить проработку», инженерные планы, ревью) работают на Claude Code, и на этом держится качество продукта. В документе не сказано, какие точки входа считаются «явным выбором». Например: кнопка проработки, профиль с движком по умолчанию, тип проекта, запуск плейбука.
**Что сломается:** при cutover флагманские сценарии незаметно перейдут на OpenCode. Качество упадёт, и формально это будет выглядеть как «работает по архитектуре».
**Предложение:** добавить короткую таблицу «точка входа → движок по умолчанию → кто может переопределить», например: проработка → Claude Code (EU); быстрый вопрос → recipe; эскалация без явного выбора → OpenCode. Записать, что настройка движка по умолчанию на уровне профиля или проекта тоже считается «явным выбором» пользователя.

### C7 · Важно · Боты-аудитории (несколько ботов на одном шлюзе) не представлены в модели

**Где:** ARCH.130 (destinationId/nativeMessageId), ARCH.150 (tg-bot: «Telegram ingress/delivery»), [Capability Catalog](CAPABILITY-CATALOG-AND-FAST-REPLIES.md) (scoped brief).
**Суть:** один шлюз уже обслуживает несколько ботов с разными аудиториями, например рекрутерский бот и @freelance_spec_bot. У каждого свой набор инструментов и свои правила. В модели нет ни сущности «аудитория/бот», ни решения, где она влияет на набор возможностей, выбор проекта и адрес доставки. contracts C02 упоминает «неправильный endpoint другого бота» как тест приёмки, но в основной модели этого измерения нет.
**Что сломается:** результат плана или файл уйдёт не тем ботом или не в тот тред. Такие баги уже были, их описывают US-03 и US-04 в [редакции user stories](trained-agent-architecture_claude_user_stories_2026-09-30_1851.md). Набор инструментов аудитории будет задаваться по-разному в разных местах.
**Предложение:** ввести audienceId (или botId) рядом с tenant/profile как измерение доступа. Он определяет каталог возможностей и адрес доставки по умолчанию. Задача запоминает audienceId и destinationId при приёме, а доставка всегда идёт по ним, а не по «текущему» боту.

### C8 · Средне · Документ читается как стопка заплаток, а статус «согласовано» не совпадает с содержанием

**Где:** ARCH.3 («актуальная согласованная целевая архитектура»), разделы-дополнения ARCH.255 («Решения 30.09.2026») и ARCH.257–263 («Уточнение перехода»), contracts/README «Уточнение владельцев v0.3», runtime «Уточнение терминов владельцем».
**Суть:** решения дописываются хвостами к разделам, которые они уточняют или отменяют. Чтобы понять текущее решение, приходится читать документ целиком и мысленно накладывать поправки. Шапка говорит «согласовано», а в таблице репозиториев половина строк помечена «предложено», «draft», «не выбран». Плотность англоязычных терминов такая, что владелец продукта без инженерного прошлого документ фактически не прочтёт.
**Предложение:** в v0.7 вплавить все «Уточнения» в основной текст, историю решений вынести в короткий DECISIONS.md (дата, решение, что отменяет). У каждого раздела поставить статус: принято, предложено или открыто. Первый экран документа написать простым языком: что строим, зачем, три ключевых решения, что остаётся открытым.

### C9 · Средне · Бюджет и доступность учёта расходов: fail-open или fail-closed не решено, а от этого зависит доступность

**Где:** INV-10, INV-11, contracts C08 («режим fail-open/fail-closed при недоступном budget authority требует решения владельца»), [MODEL-GATEWAY](MODEL-GATEWAY-AND-COSTS.md).
**Суть:** MiMo пишет об отсутствии чисел (M4), я о другом. Если учёт бюджета стоит на пути каждого вызова модели, его недоступность либо останавливает весь продукт (fail-closed), либо на это время снимает все лимиты (fail-open). Выбор влияет на доступность сильнее почти всего остального в документе, и он не сделан.
**Предложение:** по умолчанию fail-open с локальным лимитом на попытку: runner знает потолок попытки из RunSpec и сам останавливает её при превышении. Расходы пишутся в durable outbox и сверяются позже. Fail-closed включать только для платных внешних ресурсов пользователя.

### C10 · Мелочь · Две неточности, которые запутают исполнителя

- ARCH.67 и ARCH.69: «решение о следующем шаге принимает… политика Output/Router», и в той же строке «Output создаёт typed continuation». Здесь я согласен с MiMo M2 и добавляю, что проще всего снять неясность через C1: в одной базе переход — это одна транзакция одного модуля.
- ARCH.80–84 (диаграмма 3): узел `I` используется в стрелках раньше, чем объявлен с подписью `I["Input Task Queue"]` на строке 84. Mermaid это отрисует, но при чтении исходника это выглядит как опечатка.

## 4. Где я расхожусь с ревью MiMo

- **MiMo M1 и §4, «платформенную часть положить внутрь trained-assist-agent».** Это противоречит зафиксированному решению владельца (ARCH.259): новая реализация идёт в новых репозиториях, старое ядро не трогаем. Я согласен сократить число репозиториев, но новый control plane должен быть **одним новым** репозиторием (Input + Router + Output + GTD + Journal как модули с одной базой, см. C1), а не частью legacy-ядра.
- **MiMo M6, двухфазный протокол handoff.** Лечит симптом. Если выбрать одну транзакционную базу (C1) или готовый движок (C2), двухфазный протокол между Input и исполнителем не нужен.
- **MiMo M3, «перенести Integration Gate в критический путь ради HH».** Сомневаюсь: HH-сценарии сегодня работают через доменный скил, и им не нужен отдельный Gate, чтобы жить на новой платформе. На критическом пути нужна разговорная сессия (C3), потому что без неё не будет cutover ни для одного пользователя.
- С остальными пунктами MiMo (M4 числа, M5 резидентность данных, M8 отложить Watcher и Serverless API, M10 дыры изоляции, M13 срок для неизвестного исхода) я согласен и не дублирую их.

## 5. Что сделать до первой строки кода (по порядку)

1. **Решение-опора:** одна транзакционная база состояния задач (C1) и сравнение «готовый движок, свой механизм планов или с нуля» (C2). Результат — одна страница с выбором и причинами.
2. **Раздел «Разговорная сессия»** (C3), который включает выбор проекта (C4) и таблицу движков по точкам входа (C6).
3. **Правило для фич старого прода и условия cutover** (C5). Первым пилотом сделать расписание #1489 на новых контрактах.
4. **v0.7 одним текстом без хвостов-уточнений**, с DECISIONS.md и статусами разделов (C8).
После этого можно начинать I01, но первым вертикальным сценарием должна быть не фоновая задача через API, а **диалог из пяти реплик в Web с рестартом посередине**. Именно этот сценарий доказывает, что новая система может заменить старую.
