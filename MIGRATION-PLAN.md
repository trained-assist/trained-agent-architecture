# План миграции: как новая система заменяет живую

Статус: **Предложено** · v0.1 · 30.09.2026. Решения, которые нужны от владельца, собраны в разделе 8.

Этот документ отвечает на три вопроса: какие репозитории создаём и когда, в каком порядке новая система доходит до пользователей и как именно заменяется текущий прод, включая откат и вывод старого. Целевая модель — [ARCHITECTURE](ARCHITECTURE.md) (§6 что берём из прода, §9 репозитории, §10 правила перехода). Карточки работ с приёмкой — [план реализации](IMPLEMENTATION-AND-INTEGRATION-PLAN.md); здесь они только привязаны к этапам миграции. Этапы миграции обозначены M0–M6, чтобы не путать с фазами Ф1–Ф6 [плана TG/Web](TG-AND-WEB-INTERACTION-REFACTORING-PLAN.md), который правит действующий сервис.

## 0. Коротко

- **Новых репозиториев три**: `trained-assist-control-plane` — создаётся первым и нужен для перехода; `trained-assist-integration-gate` и `trained-assist-error-watcher` — позже, переход не блокируют. `ai-agent-runner` уже создан. Остальные репозитории остаются, меняется их роль (раздел 1).
- **Рубильник один — в точке приёма.** Шлюз Telegram и Web читают маршрут «профиль → старая или новая система» при приёме задачи. Принятая задача до конца живёт у выбравшего её владельца. Откат — вернуть маршрут, одна правка конфигурации (раздел 2).
- **Порядок:** M0 фундамент → M1 control plane и расписание (первый прод-трафик) → M2 Runner и диалог в Web-песочнице → M3 Telegram-песочница и домены → M4 сравнение на реальных сценариях → M5 переключение когортами → M6 вывод старого. Календарных дат нет: этап закрывается по доказательствам, а не по сроку.
- **Рабочие файлы профилей не переезжают.** Они остаются на диске VM, их читают обе системы; писатель один, потому что профиль в каждый момент принадлежит одной системе. Поэтому откат дешёвый (раздел 4).

## 1. Репозитории

### Создаём

| Репозиторий | Когда создать | Что внутри | Первая работа |
|---|---|---|---|
| **trained-assist-control-plane** | В начале M1, после выхода M0 (проверка Cloudflare на настоящем аккаунте и схема Task Store) | Task Store: схема, миграции, слой доступа; Workflow Port и адаптеры (Cloudflare Workflows, текущие планы); модули Input, Router, Output, GTD, Journal, Reporting; API для шлюзов и Web; машинные схемы контрактов | Перенос кода пилота `pilots/p-db/cf-workflows` как стартовой точки, затем расписание |
| trained-assist-integration-gate | Когда берём в работу P25 (I08) | Адаптеры провайдеров, bindings, входящий inbox, квитанции | Выделение Gate из HH-сценария |
| trained-assist-error-watcher | Когда берём в работу P27 (I09) | Ошибки → инциденты → диагностика → issue/отчёт | Агрегация по общему контракту ошибок |

Не создаём отдельно:
- **Общие контракты.** Текстом живут в [contracts](contracts/README.md) этого репозитория, машинные схемы — пакетом внутри control plane. Отдельный репозиторий — когда появится второй независимый потребитель схем (Runner или шлюз начнут их импортировать).
- **Credential Broker / Storage.** Размещение открыто (ARCHITECTURE §13). До решения используем существующее: R2 для файлов, токен Cloudflare только у сервера, токены интеграций на VM.

Каждый новый репозиторий до первой строки кода подключается к тому же конвейеру, что и прод-репозитории (I00): CI и обязательный staging, автосквош-мерж, автопочинка PR, выкладка неизменяемыми релизами.

| trained-assist-tg-bot | Остаётся единственным владельцем приёма Telegram. Добавляется адаптер к новому API и таблица маршрутов (раздел 2). Выбор исполнителя отсюда уходит в Router |

| Доменные скилы (8 штук), software-engineering-playbooks | Не переезжают. Подключаются к Runner той же схемой MCP; версия скила закрепляется вместе с релизом |

## 2. Как устроено переключение

**Точка переключения — приём.** Шлюз Telegram уже владеет приёмом и outbox запросов (ARCHITECTURE §6), поэтому рубильник ставится там, а не в ядре: так не возникает второй очереди одной и той же работы.

- В шлюзе и Web-бэкенде — таблица `backend_route`: `profileId → legacy | new`, по умолчанию `legacy`. Позже — то же для audienceId (отдельные боты).
- Маршрут читается **один раз при приёме** и записывается в квитанцию задачи. Дальше задача живёт у выбранного владельца до конца: смена маршрута влияет только на новые задачи.
- **Откат**: вернуть профилю `legacy`. Новые задачи сразу идут в старую систему. Задачи, уже принятые новой системой, она и доводит (или пользователь их отменяет); автоматически назад они не переносятся.
- Расписания с M1 живут только в новой системе, у них маршрута нет: одна реализация вместо двух.
- Кнопки, команды и `/stop` работают по владельцу задачи из квитанции, а не по текущему маршруту профиля.

## 3. Этапы

У каждого этапа — что делаем, где, условие выхода и что заметят пользователи. Этап не закрывается по «работает у меня»: нужны доказательства по правилам [Engineering Approach](ENGINEERING-APPROACH.md) и [Sandbox Plan](SANDBOX-PLAN.md).

### M0. Фундамент

Где: этот репозиторий, trained-assist-agent, аккаунт Cloudflare.
- Проверка Cloudflare Workflows + D1 на настоящем аккаунте: продолжение после сбоя без внешнего толчка, срабатывание `sleep` и тайм-аута ожидания, выкладка новой версии во время ожидания ([COMPARISON](pilots/p-db/COMPARISON.md)). Не прошла — control plane идёт на VM с DBOS + Postgres; план меняется только в месте размещения и адаптере.
- Схема Task Store v1 документом: прод-схема `state.db` плюс userTaskId, delivery, conversation, awaiting input, сигналы, журнал событий.
- Контракт разговорной сессии (ARCHITECTURE §5).
- Четыре доработки текущих планов в проде: `generation` у попытки, таблица входящих сигналов с дедупом, структурированный результат шага вместо маркера `DURABLE:`, статус `awaiting_input` и журнал. Они нужны живому сервису сами по себе и приводят прод-схему к Task Store, что упрощает перенос в M5.
- I00: общий конвейер разработки для новых репозиториев.

Выход: отчёт проверки Cloudflare; схема и контракт сессии смержены сюда; четыре доработки в проде.
Пользователи: ничего не замечают, кроме меньшего числа зависших планов.

### M1. Control plane и расписание — первый прод-трафик

Где: создаётся trained-assist-control-plane; staging-окружение на Cloudflare отдельно от прода.
- Task Store в D1, Workflow Port, адаптер Cloudflare; адаптер текущих планов — запасной.
- **Пользовательские расписания (#1489) включаются сразу на новом стеке.** Запуск расписания создаёт задачу в Task Store; пока нет нового Runner, исполнителем остаётся старое ядро через тонкий адаптер (вызов его API запуска). Это первая реальная нагрузка на Task Store и Workflow Port без риска для диалогов.

Выход: расписания работают у пользователей; проверены сбой воркера, повтор запуска того же occurrence, остановка. Откат — выключить расписания флагом.
Пользователи: снова появляются расписания.

### M2. Runner и диалог в Web-песочнице

Где: ai-agent-runner, control plane, sandbox VM (VM2), sandbox-развёртывание Web.
- Runner P01–P06: воспроизводимая среда, OpenCode, структурированные логи, принудительные сбои, приём и статус.
- Главный сценарий: диалог из пяти уточнений в Web с рестартом исполнителя между 3-м и 4-м (ARCHITECTURE §5.1).

Выход: сценарий проходит в песочнице; задержка и стоимость хода записаны рядом с текущим продом.
Пользователи: не затронуты.

### M3. Telegram-песочница и доменная работа

Где: trained-assist-tg-bot (адаптер + отдельный тестовый бот), control plane, Runner.
- Шлюз получает адаптер к новому API и таблицу `backend_route`; у всех профилей `legacy`.
- Подключение доменных скилов через Runner (P13–P15), выбор проекта на входе (§5.2), `/stop`, дополнение к идущей задаче, кнопка проработки, файлы (P07–P09).

Выход: в песочнице проходит сквозной список ARCHITECTURE §10: приём → результат → Web и чат; stop и дополнение; повтор после сбоя; бюджетный отказ; внешний callback; ожидание ответа. Плюс проекты и файлы.
Пользователи: не затронуты.

### M4. Сравнение на реальных сценариях

Где: песочница.
- Повтор обезличенных входов прода через новую систему без изменяющих внешних действий; сравнение качества, задержки и стоимости по каждому сценарию.
- Импортёр данных профиля (раздел 4) в режиме пробного прогона на копии: идемпотентный, с журналом, что перенесено.

Выход: для сценариев первой когорты новая система не хуже прода; пробный импорт профиля без ошибок.
Пользователи: не затронуты.

### M5. Переключение когортами

Порядок когорт (предложено):
1. Профиль владельца.
2. Один-два пилотных профиля и один отдельный бот (например, @freelance_spec_bot).
3. Остальные профили основного бота.
4. Остальные боты-аудитории.

Процедура для каждой когорты:
1. В issue когорты записано условие перехода: какие сценарии проходят, пороги задержки и стоимости, срок наблюдения (предложено: не меньше 7 дней реальной работы) и дата, после которой старый путь не принимает новые задачи этой когорты.
2. Импорт данных профилей когорты (раздел 4): пробный прогон, затем настоящий.
3. Переключение маршрута на `new` — в тихое окно, когда у профилей нет активной интерактивной работы.
4. Смоук на проде: пять реплик, `/stop`, расписание, файл, ответ на ожидание.
5. Наблюдение по журналам и ошибкам. Порог нарушен — откат маршрута, разбор, повтор.
6. Незавершённые задачи когорты в старой системе доводит старая. Когда они закончились (не позже 30 дней — максимальный срок ожидания ответа), старый путь для когорты закрыт на приём.

Выход этапа: все когорты на новой системе, откат не использовался весь срок наблюдения последней когорты.

### M6. Вывод старой системы

Условия: все когорты на новой системе не меньше 30 дней; в старой нет активных задач и ожиданий; данные перенесены или заархивированы; откат за этот срок не понадобился.

Шаги:
1. Удалить из шлюза и Web маршрут `legacy` и код старого пути приёма.
2. Остановить службу старого агента; последний релиз хранится, чтобы его можно было поднять.
3. Архив `state.db`, сессий и учёта расходов — в R2 с заданным сроком хранения.
4. Репозиторий trained-assist-agent перевести в архив только для чтения.

Удаление архива — отдельное необратимое решение владельца, в этот план не входит.

## 4. Перенос данных

| Данные | Сейчас | После перехода | Как и когда |
|---|---|---|---|
| Рабочие файлы профиля и проектов | Диск VM | Там же | Не переносятся. Runner монтирует их в clean room. Писатель один: профиль принадлежит одной системе |
| Проекты (указатели, активный, закреплённый) | Файлы профиля | Task Store | Импорт при переключении когорты; папки проектов на месте |
| Разговорные сессии и привязки чатов | JSON-файлы, TTL 4 ч | Task Store | Не переносим: переключаем в тихое окно, живая сессия старше 4 ч и так не продолжается. Новая сессия начинается в новой системе |
| Активные планы и ожидания | `state.db` | Остаются в старой | Доводит старая система (M5, шаг 6) |
| Завершённые планы | `state.db` | Task Store, как история | Импорт по желанию, схема уже совместима после M0 |
| Хранилище контекста скилов (context_get/set) | Файлы профиля | Task Store / KV с версией | Импорт при переключении |
| Внутренние cron-задачи | `cron_jobs` | Остаются в старой до M6 | Переносятся на расписания новой системы по одной |
| Учёт расходов | `usage.json`, `calls.jsonl` | Новый Ledger | Не переносится; новый учёт с даты переключения, старые файлы в архив |
| Страницы `publish_page` | Диск VM | R2 | Отдельная задача, переход не блокирует |
| Токены интеграций (HH, CRM и т.п.) | VM, по профилям | Там же, до решения Credential Broker | В песочницу не копируются; при переключении Runner читает их по binding профиля |

Сопоставление ID: при импорте пишется таблица соответствия старых ID задач, сессий и планов новым userTaskId, чтобы ссылки и отчёты не терялись.

## 5. Правила на время параллельной работы

- Старое ядро получает только исправления и тонкие адаптеры. Новая крупная фича проектируется сразу на новых контрактах (ARCHITECTURE §10).
- У одной работы один владелец: никакого двойного исполнения ради сравнения. Сравнение — только повтором обезличенных входов без изменяющих действий.
- Секреты и профили прода не копируются в песочницу.
- Решения прода переносятся по таблице ARCHITECTURE §6, начиная с «Как есть».
- Этап считается закрытым только с доказательствами в его issue: воспроизводимый прогон, контролируемый сбой, журналы.

## 7. Риски миграции

| Риск | Что делаем |
|---|---|
| Проверка Cloudflare на настоящем аккаунте не проходит | Control plane на VM: DBOS + Postgres. Меняется адаптер Port и размещение, этапы те же |
| Параллельный период затягивается навсегда | Новые крупные фичи только на новом стеке; у каждой когорты записана дата закрытия старого пути |
| Две системы пишут в файлы одного профиля | Профиль принадлежит одной системе по маршруту; задачи, принятые до переключения, доводит прежний владелец |
| Откат теряет данные, созданные в новой системе | Файлы профиля общие. Указатели проектов и контекст на время наблюдения первой когорты синхронизируются обратно экспортом из Task Store |
| Новая система медленнее или дороже | Пороги в условии когорты; превышение — откат маршрута |
| Кнопки и `/stop` уходят не той системе | Команды адресуются владельцу задачи из квитанции, не текущему маршруту профиля |

## 8. Решения владельца

1. **Имена репозиториев** — рекомендую принять предложенные: trained-assist-control-plane, trained-assist-integration-gate, trained-assist-error-watcher.
2. **Момент создания control plane** — рекомендую сразу после проверки Cloudflare на настоящем аккаунте, не раньше: от её результата зависит, где он развёртывается.
3. **Первая когорта** — рекомендую профиль владельца.
4. **Регион хранения RU/EU** — блокирует только когорты с требованием хранения в RU; остальные идут без этого решения.

## 9. Трекинг

Эпик миграции — issue в этом репозитории с чек-листом M0–M6. Каждый этап — дочерний issue с условием выхода и ссылками на доказательства; каждая когорта M5 — свой issue с условием перехода. Статус выполнения ведётся в issues, этот документ меняется только при изменении плана.
