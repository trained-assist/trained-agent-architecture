## 3. Замеры и проверенные факты

- **Тяжёлый профиль:** 6.8 ГБ / 155 тыс. файлов, из них настоящих текстов 4–6 МБ (замер 28.09, эпик #1784). Узлы: node_modules ×9 копий, 20 worktree на один репо, Playwright/npm-кэши 2.3 ГБ.
- **Смоук фазы (профиль-тестовик):** dry-run 16 planned → apply 16/16 (0 failed) → verify ok=16 → materialize из боевого бакета (sha/gunzip/JSON) → verify снова ok=16; на диске между Run'ами **0 тел сессий**, только `current-session*` указатели и индекс с маркерами `{key, sha256, size, at}`.
- **Dry-run тяжёлого профиля:** 494 файла / 134.9 МБ к архивации; ~48.5 тыс. записей «phase declined» (git-worktree — отдельная фаза M3); 2124 файла UNKNOWN не тронуты (чистка списка — растить по отчёту); EACCES на слот-файлах `.agent-home/tmp` (файлы движка под slot-user — чинить отдельно).
- **Инвентарь VM (28.09):** 94 профиля; 276 node_modules = 8.84 из 14.51 ГБ; `opencode.db` 1.17 ГБ (один на VM, класс SYSTEM — в архив не идёт); `playwright-storage-state.json` в 86/94 профилях; `.mcp.json` с plaintext AGENT_SECRET в 10/22.
- **Бакет:** object storage с versioning; у VM сервис-аккаунта `storage.objectAdmin`; доступ с legacy VM подтверждён ADC (без ключевых файлов).

## 4. Решения владельца, которые переносятся как есть

1. **Q1 (потери при принудительном перехвате):** push в конце сессии после текстофикации; самозапрет старой VM по TTL; zombie-push = non-fast-forward, не тихая перезапись. Окно потери = незалитая работа текущей сессии (~1 мин) — принято.
2. **Q2:** непрерывная репликация SYSTEM_ROOT не нужна; гибель VM = перезапуск задачи с тем же инпутом.
3. **Q3:** транскрипты — в sync-набор (materialize обязателен); секреты в workspace — EXCLUDE, наружу никогда; «секрет нечитаем с диска» = at-rest шифрование + нет plaintext-копий в выгрузках + сервисные ключи не в env движка.
4. **Q-C:** доступ «мои данные» = приватное git-репо на юзера + collaborator по запросу (орга `profiles-artifacts` создана, токен узкий, в Secret Manager).
5. **Требование владельца (зафиксировано в legacy #1921):** конфликт при push — редкое событие, разрулить должна **дешёвая сессия-фиксер** (fetch → merge → авто-резолв «файл создался дважды»), лимит 2 попытки, дальше оператор; **force-push запрещён всегда**.

## 5. Ловушки, выученные на red-team и в эксплуатации

- **Admission-хук строго до резолва сессии:** иначе `getSession → null` молча создаёт слепую новую сессию (потеря продолжения без ошибки).
- **Verify до удаления:** sha загруженного должен совпасть с локальным до unlink; иначе краш = потеря безвозвратная.
- **Flush до снапшота:** буферизованные JSONL (30 с) иначе создают «отставшую» копию; endpoint flush обязан отвечать 500, пока записи в буфере.
- **Профиль — scope блокировки:** параллельные раны одного профиля при мутации паркуются; control-команды (/stop, read-only) обходят лок.
- **Синхронные читатели вне рана** — главный риск materialize: каждый вызывающий должен либо ждать materialize, либо читать индекс, либо быть async (аудит сделан в #1933).
- **`.agent-home` переживает запуски** (CODE-BASELINE §2) — в целевой модели runtime state получает/отдаёт clean room, а не живёт в профиле.
- **Native resume ключуется от slug абсолютного cwd** — при переезде профиля slug пересоздаётся, иначе lossy-fallback (в legacy: ~8×1500 символов вместо полного транскрипта).

## 6. Чего НЕ переносить (сверено с CODE-BASELINE)

- Локальный `execution-owner-lock` как решение межмашинного владения → capacity lease + generation.
- `opencode.db` как журнал сессий (ограничен, 4000 событий, только OpenCode) → журнал по OBSERVABILITY-контракту.
- Доставку ответа агентом напрямую в Bot API → Output-модуль + outbox (уже заменено в проде частично).
- `DURABLE:`-маркер как протокол результата → структурированный результат шага (M0-доработка).
- Дубли чтения токенов в скилах (сырой `fs.readFileSync`) → Credential Broker; до этого — грейс-режим legacy-стора.
