## 0. Короткие ответы

| Вопрос | Ответ |
|---|---|
| Пока идёт/ждёт задача, я пишу ещё — они без ответа? | **Нет.** Сообщение попадает в держатель (`buf` Durable Object `IntakeBuffer`) и через 1.5 с получает квитанцию «✓ Получил ещё N сообщений…» с меню. Само по себе оно **никогда не выполняется** и **никогда не подмешивается в работающую задачу автоматически** — только (а) тап «▶️ В очередь…», (б) судья тишины при следующем сообщении, (в) модель сама дёрнула `get_new_messages` (live inbox) — тогда сообщение обработано **внутри текущей задачи** и из держателя исчезает (`consumed`). |
| Попадают ли они во вторую (ждущую) задачу? | **Да — если нажата «▶️ В очередь после текущей»**: при освобождении окна весь буфер (текст задачи-2 + новые сообщения) уходит **одним** `/run` (`coalesceBuffer`, `intake-routing.js:66`). В агентскую очередь (admission lane) задача-2 попадает не «ждали в боте», а только после этого запуска — **в обычном флоу задача-2 вообще не уходит в агент, пока не отпустили окно** (`launchAfterRelease` — флаг в DO, `intake-buffer.js:651`). Если тапа не было — сообщения ждут в коллекторе с ▶️ и **не стартуют сами** (`intake-buffer.js:1254-1256`). |
| Почему «работа агента вниз не переезжает» | Один и тот же пузырь редактируется на месте: коллектор/квитанция — `editMessage` (`intake-buffer.js:1032-1046`), при запуске он же становится `initialMsgId` (`intake-buffer.js:1106-1108`), и агент весь ран редактирует именно его (tg: `editMessageText`). Новые сообщения при этом появляются **ниже**, поэтому работа «залипла» наверху. Это свойство `edit-in-place`, а не баг очереди. |
| Это тг-бот или не он? | **Двухслойно.** Приём, держатель, квитанции, кнопки и рендер сообщений остаются в тг-боте (блок **A01**, контракт **C01/C02**, вердикт ARCH §6 — буфер «Как есть, сопоставить с C01 без переписывания»). Очередь/admission, явный выбор «в очередь/параллельно», статусы и supplement уходят в **control plane** (C01: «orchestrator — за task/session/project/admission»; статусы — Task Reporting, P05/P12; supplement — C03). «Выбор исполнителя отсюда уходит» — ARCH §9, строка `trained-assist-tg-bot`. |

## 2. Машина busy/idle и что происходит с сообщениями

Состояния Durable Object описаны в шапке `src/intake-buffer.js:15-26`:

- **idle** — сообщения копятся, коллектор показывает ▶️ + счётчик, вооружён тихий гейт (3 мин, судья);
- **busy** — «ран уже идёт: новые сообщения копятся молча и после рана предлагаются кнопкой запуска (**никогда не автодиспатчатся**)».

**Где ставится busy:** только первый ран окна — `_dispatch` `src/intake-buffer.js:1073-1078`; сопровождается **сетом requestId** (`busyRequestIds`, #321) — `:1131-1134`, жить до последнего рана окна `:476-480` (в этом механика Ф4 «⚡ Параллельно», #322).

**Где снимается:** `/internal/run-finished` от агента (`src/index.js:36-58` → `intake-buffer.js:456-486`, матч по requestId), перманентный reject outbox (`run-outbox.js:58-67`), самопроверочный пол `/tasks/running` раз в минуту (`intake-buffer.js:1266-1290`), потолок `BUSY_MAX_MS=45м` (`:1395-1410`).

**Поведение M1/M2 (ваши «ещё сообщения») во время busy:**

1. держатся в `buf` + одна отложенная квитанция (1.5 с) — `:562-565`, текст `heldText` `:112`;
2. на экране — тот же пузырь: если нажата «В очередь», показывает «⏳ Порция из N…» со счётчиком, куда M1/M2 уже входят (`:1013-1028`);
3. **никогда не вливаются в уже принятый агентом ран** — в гейте нет append-to-run (`/append` — имя ловушка: он только кладёт в `buf`, `:571-584`);
4. исходы при освобождении окна:
   - нажата «▶️ В очередь» (`launchAfterRelease`) → **один новый `/run`** со всем буфером (`:1242-1245` → `_dispatch`, `coalesceBuffer`) — так что M1/M2 выполняются **вместе с задачей-2 как один input**;
   - нажата «⚡ Параллельно» (#322) → немедленный отдельный ран в новой сессии (`:621,636-649`);
   - ничего не нажато → коллектор с ▶️, ждут indefinitely: тап / новое сообщение (судья) / форс-слово (`:1254-1256`, `:1329-1357`);
   - модель успела забрать через **live inbox** (`GET /internal/held-messages` → MCP `get_new_messages`, `src/index.js:64-79`, `agent: src/live-inbox.js:7,60`) → item помечен `consumed` и удаляется из буфера на run-finished (`:466-472`) — **это единственный путь, где сообщение уходит из системы без отдельной гарантии ответа**.

**Два разных «вторая задача ждёт первой»** — код различает их, документы часто путают:

| | Механика | Кто знает |
|---|---|---|
| **A. Держатель бота** (обычный флоу «В очередь») | задача-2 лежит в `buf`, флаг `launchAfterRelease`; агент её **не видел** | только DO |
| **B. Admission lane агента** | `/run` ушёл мимо intake (команда-форвард `handlers/commands.js:80,130,329`, `plan|` `callbacks.js:680`, FIFO outbox `run-outbox.js:30-96`, ⚡ параллельно) и ждёт lane (`trained-assist-agent` → «Ожидаю завершения…») | только агент; DO про него **не знает** → его `run-finished` попадает в `mismatch` и не продлевает/не снимает окно (`intake-buffer.js:461-462`) |

## 3. Почему работа «залипает» наверху

Одна точка правды — `_showCollector` (`src/intake-buffer.js:1004-1049`):

1. есть `collectorMsgId` → **edit того же сообщения** (`:1032-1036`);
2. при запуске коллектор переписывается в «📨 Передаю собранный input агенту…» и становится `initialMsgId`, сам `collectorMsgId` удаляется (`:1106-1108`);
3. дальше весь ран агент редактирует **это же сообщение** (`agent-client.js:124-125` → агент `runner`/`claude-runner` progress-edit);
4. новое сообщение создаётся только когда старого нет (нет prevId / message not found, `:1043-1046`).

Инвентарь edit vs new (по origin/main):

| Что | edit «на месте» | new «внизу» |
|---|---|---|
| Коллектор, квитанции, held/queued/stopped, «📨 Передаю…» | ✅ `intake-buffer.js:1032-1106` | при первом создании |
| Прогресс и финальный ответ агента | ✅ правится `initialMsgId` | фолбэк `sendMessage`, если edit невозможен |
| Кнопки стопа/дополнения (`stop|`,`supok|`) | ✅ edit своего сообщения `callbacks.js:849-923` | — |
| «⏳ Идёт текущая задача…», «⚡ Запускаю параллельно…», «↩️ Отменить» | — | ✅ `callbacks.js:644,630,661` |
| Коллектор после рана (остатки) | — | ✅ новый, якорь на последнем held `:1255-1256`, `:1043` |

Следствие для новой модели: «одно статус-сообщение на запуск» — это **требование** (U-21), а «статусы не редактируют чужие сообщения» — инвариант RC-03; механизм (`editMessage` пузыря) сейчас целиком в боте и рендерится как C02.

## 5. Дыры, найденные при ревью (это и есть «what to review»)

1. **SS-05 выполнен наполовину.** Спека Core 02 требует: при Стопе — `launchAfterRelease` сброшен ✅, **outbox-запись отменена ❌, retry-запись удалена ❌**. Стоп (#308, `intake-buffer.js:393-429`) чистит флаги и таймеры, но ни один путь не отменяет job в `RunOutbox` (удаляется только на успех `run-outbox.js:79` / перманент-reject `:62`) и не убивает `retry:`-запись (`src/lib/kv.js:112-148`). **Задача, стоящая в outbox или в recovery-очереди до Стопа, после Стопа всё равно уйдёт/восстановится.**
2. **Случай B — теневое окно.** Второй `/run` мимо intake не попадает в `busyRequestIds`; его `run-finished` → `mismatch` (`:461-462`). Окно живёт только от «своих» ранов — двойной счёт (агент занят, бот считает свободно) возможен в обе стороны.
3. **Потерянный батч без ack.** Если `handleMessage` не вызвал `onRunAccepted` (пикер проекта, «сначала войди», fileTooLarge…), `_releaseBusyLocked` удаляет `launching`, а `buf` уже пуст (`:1148-1152`, `:1218`; `message.js:104-108`) — часть батча уходит без повторного предложения. Частичные mitigation'ы есть (пикер сохраняет ввод, `lib/project-choice.js:72-94`), «not logged in» — нет.
4. **`consumed` без гарантии.** Item, забранный моделью через live inbox, удаляется из буфера на run-finished (`:466-472`); ответил ли модель — решает только агент. Единственная «тёмная» дыра «без ответа».
5. **Изменение перманент-reject outbox:** payload остаётся `failed:<id>`, но редиспатча нет (`run-outbox.js:58-67`).
6. **Дрейф документации.** `docs/user-stories/CURRENT-STATE.md:80-88` (US-BUF-04 «reply — байпас буфера», ✅) и `docs/INTAKE-SCENARIO-MATRIX.md` §5 **противоречат коду**: reply буферизуется (`intake-routing.js:26-36`, тест `tests/route-text.test.js:72-79`). В `stories/TRACEABILITY.md` это уже помечено как открытый аудит A-2 («→ Ф6»).
7. **`/clean_buffer` в busy отвечает отказом без отложенного очищения** (`commands.js:673-688`) — пользователь должен повторить команду.
8. **Дополнение в боте всё ещё «стоп+рестарт»**: `supok|` делает `stopTask` + `handleMessage` (`callbacks.js:902-937`), а на агенте с 30.09 есть серверный `POST /tasks/supplement` (trained-assist-agent #1943, контракт — в теле PR). Перевод бота на него — известный follow-up.

## 6. Куда это переезжает в новой архитектуре (ответ «бот или нет»)

Документы отвечают явно; расщепление такое:

| Механизм сегодня | Целевой владелец | Основание |
|---|---|---|
| Держатель (`buf`), квитанции, коллектор, кнопки, медиа-prep | **tg-bot (A01)** — «Как есть, сопоставить с C01 без переписывания» | ARCH §6 (строка «Шлюз Telegram: буфер приёма, outbox…»), §9; `TASK-ROUTER-AND-MCP.md` §8: «native normalization/receipts оставляем gateway» |
| Меню «В очередь / Параллельно» (UI) и его флаг | **tg-bot** шлёт флаг; **проверка** — admission | INV-03: «флаг `parallel` из launch-меню шлюза», RC §3; фазы Ф3/Ф4 плана |
| Очередь/admission, session/lane, сам запуск | **control plane (orchestrator)**, контракт C01/C03; сейчас — агент `src/core/admission.js` | contracts C01 «orchestrator — за task/session/project/admission»; RC §5 |
| «Занят/ждёт/выполняется» — статусы | **Task Reporting** (read model, P05/P12), без LLM | `USER-TASK-IDS-AND-REPORTING.md` §2/§4; INV-15 |
| Подмешать в работающую задачу / supplement | **C03** (owner Input/GTD), UX — меню RC-04 (заменяет кнопку «➕ Дополнить») | contracts C03; RC §3; U-13/API-09 |
| Рендер прогресса/ответа в Telegram (edit-in-place) | **tg-bot рендерит события** C02; события идут из Output — прямой Bot API из агента «Заменяем» | contracts C02; ARCH §6 |
| Молчаливый `launchAfterRelease`, тихий судья-автозапуск в busy | **выпиливаются** | план Ф6 |

Важные привязки:

- Фазы Ф1–Ф6 старого плана **не отменены** новой архитектурой: «ближний контур… правки действующего кода; при pilot/cutover становятся reference-контрактами» (`TG-AND-WEB-INTERACTION-REFACTORING-PLAN.md` §1, §6).
- «Busy» как **теневая система статусов** (set requestId в DO, полы, `BUSY_MAX_MS`) — это местный прототип Reporting: на новой модели состояние «идёт/ждёт/в очереди» читается из Reporting, а не выводится из «мой `/run` был принят» (см. дыру §5.2 — она исчезает вместе с дублем).
- Первый интеграционный сценарий («диалог из пяти реплик с рестартом», I03 · P10+P12, ARCH §5.1) проверяет **последовательную** преемственность реплик, а **не** поведение «сообщения во время задачи» — для этого U-12/U-13, у которых карточек нет (см. §7).

## 7. Что ревьюить при переносе (чеклист)

**A. Механизмы из §4 — по одному пункту на файл:**

- [ ] `shouldDebounce`/`coalesceBuffer` → сверить с C01 (сбор пачки, нормализация — у gateway; binding policy нескольких сообщений к открытому intake **в архитектуре ещё не задана**, `USER-TASK-IDS-AND-REPORTING.md` §1);
- [ ] busy-окно (`busyRequestIds`, poll, `BUSY_MAX_MS`) → заменить чтением Reporting; что делать с legacy-счётчиком до P05 — явно зафиксировать;
- [ ] `launchAfterRelease`/тихий судья → Ф6 удаляет; чем заменяется автозапуск — решение (ОВ-2 сценария RC);
- [ ] live inbox (`consumed`) → C03 + PR-01 «на каждую реплику ровно один итог»: исчезновение из буфера должно быть обосновано событием в журнале;
- [ ] `RunOutbox`/`RetryQueue` → C01/C02 (outbox запросов «Как есть»), **но сначала закрыть SS-05 п.1** — отмена job/retry при Стопе;
- [ ] `initialMsgId`-цепочка (коллектор → ран) → C02: одно статус-сообщение на запуск (U-21), «статусы не редактируют чужие сообщения» (RC-03), markup-clear (RC-07/Ф1);
- [ ] `sup|`-флоу → серверный `POST /tasks/supplement` (агент #1943) + C03;
- [ ] `/debug/intake/.../flush` — escape hatch: остаётся в новом gateway или заменяется Reporting/API?

**B. Инварианты, которые обязаны переехать как есть:**

INV-03 (lane по умолчанию, параллель только явным флагом) · «одна реплика — ровно один итог» (PR-01) · receipt-семантика «✓ Получил… ≠ запущено» (U-12 шаги) · одна сессия/лента на диалог · Стоп гасит и очередь (SS-05, включая пп. outbox/retry) · «Получил ещё N» не редактирует чужой прогресс (RC-03).

**C. Пробелы в плане (закрывать до переноса, не после):**

- **U-12** «явный выбор при новой задаче во время идущей» — карточки нет (рекомендация stories/README: P12+P10/P11);
- **U-13 / API-09** «передать данные работающей задаче» — только контракт C03, в API-спецификации нет;
- **U-21** «видеть фоновую работу» — отдельной карточки нет;
