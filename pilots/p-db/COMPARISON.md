## Выводы, общие для всех вариантов

1. **Fencing всегда наш.** Ни один движок не защищает записи в нашу базу. Поле `generation` у попытки и условная запись `UPDATE … WHERE generation = ?` обязательны в Task Store при любом движке (INV-02).
2. **Окно повторного внешнего вызова есть у всех.** Если процесс падает после внешнего действия, но до записи шага, шаг выполнится ещё раз. Внешние вызовы нужно делать идемпотентными по ключу (userTaskId, шаг). В прод-схеме для этого уже есть `hook_executions.boundary_key UNIQUE`.
3. **Сигналу нужен свой ключ идемпотентности**: id входящего сообщения, который передаёт Input. Без него у DBOS второй ответ остаётся в очереди и его заберёт следующее ожидание, а у текущих планов второй ответ перезаписывает первый.
4. **Статус движка расходится со статусом задачи.** После kill -9 Cloudflare показывает `running`, хотя задача ждёт ответа. Это подтверждает INV-20: Reporting читает статус только из Task Store.
5. **Имена и порядок шагов — это контракт версии.** Экземпляр, который ждёт ответа до 30 дней, продолжит работу на новом коде (Cloudflare) или будет привязан к старой версии (DBOS, Restate). Переименование шага означает его повторное выполнение. Отсюда правило: шаги только добавляются, переименование считается новой версией плана.

## Рекомендация

1. **Цель — Cloudflare Workflows + D1 (управляющий слой на Cloudflare рядом со шлюзом).** Все проверки пройдены. Своих процессов, бэкапов и апгрейдов движка нет, а для одного владельца это главный критерий. D1 — тот же SQLite, поэтому прод-схема переносится почти без правок. Шлюз, web и ladder уже на Cloudflare. **Условие:** одна проверка на настоящем аккаунте Cloudflare, потому что локальный эмулятор после kill -9 сам не продолжает (в нём нет таймеров). Нужно подтвердить: (а) экземпляр, прерванный между шагами, продолжает сам, (б) `sleep` и тайм-аут ожидания срабатывают без внешнего события, (в) деплой новой версии во время ожидания. **→ Условие закрыто 01.10.2026: все три подтверждены на реальном аккаунте, см. [CLOUD-SMOKE.md](CLOUD-SMOKE.md).**
2. **Запасной вариант — DBOS + Postgres (управляющий слой на VM).** Результат лучший по строгости: сигнал и запись истории идут одной транзакцией в одной базе, а сам DBOS — библиотека, не отдельный сервер. Цена — сопровождение Postgres. Выбираем его, если проверка на Cloudflare не пройдёт или если регион хранения данных запретит Cloudflare.
3. **Restate исключаем.** Он добавляет постоянно работающий сервер с состоянием (150–250 МБ) и лицензию BSL, а по нашим проверкам ничего сверх DBOS не даёт.
4. **Текущие планы остаются рабочим адаптером** на время миграции. Четыре доработки нужны при любом выборе, потому что это и есть схема Task Store:
   - `generation` и аренда у попытки с проверкой при каждой записи (T6);
   - входящие сигналы отдельной таблицей с типом события и дедупом по id (T4, T5);
   - структурированный результат шага вместо текстового маркера `DURABLE:`;
   - статус `awaiting_input` и журнал событий; отмена закрывает шаги и отвергает пробуждение (T7).

   Срочным багом в проде это не является: по коду прогон ограничен 40 минутами при льготе 45 минут, а ответ пользователя обычно приходит уже после того, как шаг встал в ожидание. Но это пробелы контракта, которые закрываются первыми.
