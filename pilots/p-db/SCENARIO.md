# Пилот P-DB — общий сценарий (ARCHITECTURE.md §4.5)

Каждый вариант реализует ОДИН и тот же сценарий через тонкий Workflow Port
(start / step / waitFor / signal / cancel / status) и отдельный Task Store
(источник истины: статус задачи — колонка, история — таблица событий).

## План из 5 шагов (userTaskId = "ut-pilot-<n>")
1. prepare  — пишет событие в Task Store, инкремент side-effect счётчика `prepare`.
2. run      — «внешний вызов»: инкремент счётчика `run` (файл/таблица side_effects).
3. wait     — waitFor("user_reply", timeout 24h). Задача в Task Store = awaiting_input.
4. apply    — использует payload ответа (ожидается {"answer":"да"}), счётчик `apply`.
5. finalize — статус задачи done, результат в Task Store.

## Обязательные проверки (каждая → PASS/FAIL/N/A с доказательством из лога)
- T1 happy path: все 5 шагов, status=done, в истории 5 шагов.
- T2 crash after step 2: процесс-исполнитель убивается `kill -9` сразу после завершения шага 2
  (до начала шага 3). После рестарта: шаги 1–2 НЕ выполняются повторно (счётчики prepare=1, run=1),
  сценарий продолжается.
- T3 ожидание без ресурсов: пока задача ждёт ответа, исполнитель полностью остановлен
  (нет живого процесса / слота). Затем приходит signal, исполнитель поднимается — задача доходит до done.
  Отметить: нужен ли вообще живой процесс во время ожидания и сколько он ест (RSS).
- T4 ранний сигнал: signal("user_reply") отправлен ДО того, как экземпляр дошёл до waitFor —
  событие не теряется.
- T5 дубль сигнала: signal отправлен дважды — шаг 4 выполнен один раз (apply=1).
- T6 fencing: «устаревший исполнитель» (старое generation / старая попытка) пытается записать
  результат шага — запись отвергнута, состояние не изменилось.
- T7 cancel: отдельный экземпляр, отменённый во время ожидания, не возобновляется
  после сигнала и рестарта (INV-08).
- T8 наблюдаемость: статус и история задачи читаются из Task Store одним SQL-запросом
  (приложить запрос и вывод).

## Метрики
- Строк кода адаптера (без тестов), число движущихся частей (процессы/сервисы/БД).
- Время прохода T1 (wall clock), задержка signal→step4.
- Что нужно для прод-эксплуатации одним человеком (бэкап, апгрейд, мониторинг).
- Перенос текущей схемы `durable-tasks/state.db` (durable_tasks, task_items, executions): как ложится.
- Честные ограничения: что проверено локально, а что только по документации.

## Результат каждого варианта
`pilots/p-db/<variant>/` : код, `run.sh` (воспроизводит всё одной командой), `RESULTS.md`
(таблица T1–T8 + метрики + выводы), `results.json`. node_modules и бинарники не коммитить.
