# P-DB: облачный smoke на реальном аккаунте Cloudflare (эпик #87, A1)

Дата: 01.10.2026. Основание: [COMPARISON.md](COMPARISON.md) → «Рекомендация, п.1: **Условие — одна проверка на настоящем аккаунте Cloudflare**» с тремя пунктами (а), (б), (в).
Локальный пилот до этого проходил 8/8 только в эмуляторе `wrangler dev`; здесь всё то же выполняется **в продакшене Cloudflare**.

## Как воспроизводится

```bash
cd pilots/p-db/cf-workflows
NODE_ENV= npm install            # wrangler 4.145.0 (нужен Node ≥ 22)
./cloud/cloud-run.sh             # один прогон всех трёх критериев, ~6–10 минут
```

Выход: `cloud/cloud-run.log`, `cloud/results.cloud.json`, `cloud/evidence-*` (логи ранов, SQL из удалённой D1, tail).

### (а) Продолжение после сбоя без толчка

Два независимых наблюдения (одного kill -9 над инфраструктурой Cloudflare мы наверняка не воспроизведём — ей владеет платформа, см. «Честные ограничения»):

1. **Сбой шага → платформа сама продолжает.** В плане `crashRunOnce`: шаг `guard-crash` бросает ошибку на первой попытке (аналог «исполнитель упал сразу после шага 2»), ретраи `{limit:3, delay:2s}`. Из `evidence-c1-instance.txt` (финальный прогон):

   ```
   Name: guard-crash-1   Duration: 2 seconds   Success: ✅ Yes
   │ 9:38:25 pm │ 9:38:26 pm │ 0 seconds │ ❌ Error │ Error: injected executor crash between steps (attempt 1) │
   │ 9:38:28 pm │ 9:38:28 pm │ 0 seconds │ ✅ Success │                                                   │
   Status: ✅ Completed   Last Successful Step: finalize-1
   ```

   Внешних событий в этот момент не было вообще. Завершённые шаги не повторились: `side_effects = {"prepare":1,"run":1,"apply":1}` (см. `results.cloud.json → evidence.C1`), история `prepare → run → guard-crash → wait → apply → finalize`.
2. **Долгое отсутствие живого процесса → платформа сама будит.** Экземпляр спит в `step.sleep` 45 с: между `step_done run` и `status wait` прошло **45.2–47.4 с** (финальный прогон: 47 390 мс), за это время в инстанс **ноль событий** (см. `C2 mid-sleep: {"status":"running","steps":["prepare","run"],"signals":0}`), после пробуждения он сам дошёл до `awaiting_input`. Шаги 1–2 не перезапускались.

Локальный вывод «движку miniflare нужен `Port.recover()`» на проде подтвердился как **не нужный**: платформа возобновляет экземпляр по таймеру и по сбою шага сама, `recover()` в облачном прогоне не вызывался.

### (б) Sleep и тайм-аут ожидания без внешнего события

- **Sleep:** см. (а) — 45 с спокойного ожидания без единого запроса к воркеру, затем продолжение.
- **Тайм-аут `waitForEvent`:** задача `ut-cf-*-timeout` с `waitForTimeoutSec=20` **не получила ни одного сигнала** и через **22.2–22.9 с** сама закрылась: `status=failed`, `result={"reason":"user_reply_timeout"}`, в истории ровно одно `wait_timeout`, `signals=0`, движок `complete` (не завис в ошибке). Дедлайн сработал без всякого внешнего события.
- Попутно подтверждено свойство платформы, которое надо знать: пока инстанс уходит в ожидание, `wrangler tail` показывает `outcome=exception` c сообщением *«runtime canceled this request because it detected that your Worker's code had hung»* и `event.rpcMethod="run"` (`evidence-tail.jsonl`). Это отмена заблокированного вызова `run()` при уходе в hibernation, а не сбой задачи: Task Store тем временем в `awaiting_input`, после сигнала всё дорабатывает. Reporting-статусы читаем из Task Store (INV-20) — и это ещё одно подтверждение, что статус движка врёт.

### (в) Деплой во время ожидания

Сценарий: задача в `awaiting_input` (версия кода **v1** записана в `mark-awaiting`) → `wrangler deploy` с маркером **v2** (файл `src/version.ts`, переписывается и восстанавливается автоматически) → задача после деплоя осталась `awaiting_input`, не упала → через 60 с `POST /signal` → дошла до `done`.

Ключевое доказательство финального прогона из `evidence-d1-status.json` (одним SQL к удалённой D1):

```
mark-awaiting payload: {"waitingFor":"user_reply","version":"v1"}   ← ждала на старом коде
apply         payload: {"used":"да","version":"v2"}                 ← после сигнала выполнила НОВЫЙ код
result_json:           {"answer":"да","ok":true,"version":"v2"}
```

Экземпляр пережил деплой и возобновился на свежезадеплоенном коде — то самое правило «имена и порядок шагов = контракт версии» из COMPARISON.md подтверждается, но с уточнениями ниже.

**Наблюдения по четырём прогонам (все — деплой во время ожидания):**

| Прогон | Что было | signal → apply | Код шагов после сигнала |
|---|---|---|---|
| 181011 | сигнал через 5 с после деплоя | **50 290 мс** | **v2** (новый) |
| 181749 | сигнал одновременно с окончанием деплоя + второй деплой через ~1.5 мин | **269 760 мс** | v1 (второй деплой уже вернул v1) |
| 183121 (финальный) | сигнал через ~0–4 с после деплоя | **316 мс** | **v1** — новый код ещё не «доехал» до инстансов |
| 183802 (финальный, с окном 60 с) | сигнал через 60 с после деплоя | **1 425 мс** | **v2** (новый) |

Два вывода, оба оформлены в issues:

1. **Пробуждение сразу после деплоя непредсказуемо по латентности** (316 мс … 270 с) — issue [#91](https://github.com/trained-assist/trained-agent-architecture/issues/91). Без деплоя на тех же задачах 234–627 мс стабильно.
2. **Новый код до инстансов доезжает с задержкой ≥6 с после возврата `wrangler deploy`** (прогон 183121 проснулся через 316 мс и выполнил v1; через 60 с после деплоя — уже v2) — issue [#92](https://github.com/trained-assist/trained-agent-architecture/issues/92). Практическое следствие: если деплой содержит смену логики, полагаться на новый код у ожидающих экземпляров можно только после окна пропагации; имена/порядок шагов менять нельзя в любом случае.

## Найденный баг (блокер контракта Task Store, не выбора площадки)

Один раз у **уже завершённого** экземпляра (`done` в 18:13:12Z) через 3 мин 48 с в `task_events` пришло позднее `wait_timeout`, и статус в `tasks` перезаписался `done → failed` при том же `generation=1`. Движок (`instances describe --json`: `status=complete`, все шаги Success, error=null) об этом «не знает» — запись появилась только в D1. Повторно не воспроизводилось (**0 перезаписей у 10 следующих завершений**) → issue [#90](https://github.com/trained-assist/trained-agent-architecture/issues/90).

Вывод для A2/B1: **generation-фенсинга недостаточно** — терминальные статусы (`done/failed/cancelled`) обязаны быть неизменяемыми (guard в `commitStep`), и `catch` тайм-аута не должен писать `failed` поверх `done`. На выбор движка это не влияет: это наш слой Task Store.

## Что проверено запуском, а что по документации

**Проверено на реальном аккаунте (этот прогон):** все три критерия (а)(б)(в) выше; платформенные ретраи шага; авто-пробуждение по таймеру `sleep`; срабатывание тайм-аута `waitForEvent` и `try/catch` вокруг него; буферизация/приём сигнала; отмена зависшего `run()` при уходе в ожидание; чтение Task Store одним SQL из удалённой D1; `instances describe/list` как источник доказательств.

**Только документация (не проверялось):** цены и точные лимиты тарифов (free включает 3000 steps/день, 100k req/день, 10 мс CPU/инвокацию; биллинг steps/storage для Paid — с 10.08.2026); D1 Time Travel; хранение истории экземпляров 30 дней; поведение при hundreds одновременно ожидающих экземпляров; региональные ограничения (D1 создана в EEUR — регион хранения данных нужно сверить с требованиями до прод-решения).

**Не проверялось принципиально:** настоящий `kill -9` инфраструктуры Cloudflare — ею владеет платформа; вместо него использованы воспроизводимые аналоги (ошибка шага = сбой исполнителя, hibernation = исчезновение живого процесса).

## Вердикт A1

**Control plane на Cloudflare годится — выбираем Cloudflare Workflows + D1.** Все три условия из COMPARISON.md пройдены на реальном аккаунте с доказательствами в `cloud/evidence-*`. Запасной вариант DBOS + Postgres на VM остаётся запасным (не нужен по итогу A1).

Условия принятия решения, которые вытекают из прогона (не меняют выбор площадки, но обязательны к учёту в M1/A2):

1. **Терминальные статусы защищаются в Task Store** — issue [#90](https://github.com/trained-assist/trained-agent-architecture/issues/90) (generation-фенсинга одного недостаточно).
2. **Деплой во время активного ожидания допустим** (экземпляры выживают и берут новый код), но пробуждение после деплоя непредсказуемо по латентности — issue [#91](https://github.com/trained-assist/trained-agent-architecture/issues/91); SLO очереди сигналов закладывать с запасом либо деплоить в паузах.
3. **Новый код до ожидающих инстансов доезжает ≥6 с после возврата `wrangler deploy`** — issue [#92](https://github.com/trained-assist/trained-agent-architecture/issues/92): additive-деплои обязательны, логика шагов не должна зависеть от того, успела ли пропагация.
4. **Шаги держать лёгкими** (CPU 10 мс/инвокацию на Free) либо закладывать Workers Paid; тяжёлые side effects — через D1/очереди с идемпотентностью по `(userTaskId, шаг)`.
5. Регион D1 (EEUR) и юридические ограничения региона хранения — сверить с требованиями владельца до прод-миграции (по COMPARISON.md это единственное, что могло бы сместить решение в DBOS).
