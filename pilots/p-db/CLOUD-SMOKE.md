
### (а) Продолжение после сбоя без толчка

Два независимых наблюдения (одного kill -9 над инфраструктурой Cloudflare мы наверняка не воспроизведём — ей владеет платформа, см. «Честные ограничения»):

1. **Сбой шага → платформа сама продолжает.** В плане `crashRunOnce`: шаг `guard-crash` бросает ошибку на первой попытке (аналог «исполнитель упал сразу после шага 2»), ретраи `{limit:3, delay:2s}`. Из `evidence-c1-instance.txt` (финальный прогон):

   ```
   Name: guard-crash-1   Duration: 2 seconds   Success: ✅ Yes
   │ 9:38:25 pm │ 9:38:26 pm │ 0 seconds │ ❌ Error │ Error: injected executor crash between steps (attempt 1) │
   │ 9:38:28 pm │ 9:38:28 pm │ 0 seconds │ ✅ Success │                                                   │
   Status: ✅ Completed   Last Successful Step: finalize-1
   ```

   Внешних событий в этот момент не было вообще. Завершённые шаги не повторились: `side_effects = {"prepare":1,"run":1,"apply":1}` (см. `results.cloud.json → evidence.C1`), история `prepare → run → guard-crash → wait → apply → finalize`.
2. **Долгое отсутствие живого процесса → платформа сама будит.** Экземпляр спит в `step.sleep` 45 с: между `step_done run` и `status wait` прошло **45.2–47.4 с** (финальный прогон: 47 390 мс), за это время в инстанс **ноль событий** (см. `C2 mid-sleep: {"status":"running","steps":["prepare","run"],"signals":0}`), после пробуждения он сам дошёл до `awaiting_input`. Шаги 1–2 не перезапускались.

Локальный вывод «движку miniflare нужен `Port.recover()`» на проде подтвердился как **не нужный**: платформа возобновляет экземпляр по таймеру и по сбою шага сама, `recover()` в облачном прогоне не вызывался.

### (б) Sleep и тайм-аут ожидания без внешнего события

- **Sleep:** см. (а) — 45 с спокойного ожидания без единого запроса к воркеру, затем продолжение.
- **Тайм-аут `waitForEvent`:** задача `ut-cf-*-timeout` с `waitForTimeoutSec=20` **не получила ни одного сигнала** и через **22.2–22.9 с** сама закрылась: `status=failed`, `result={"reason":"user_reply_timeout"}`, в истории ровно одно `wait_timeout`, `signals=0`, движок `complete` (не завис в ошибке). Дедлайн сработал без всякого внешнего события.
- Попутно подтверждено свойство платформы, которое надо знать: пока инстанс уходит в ожидание, `wrangler tail` показывает `outcome=exception` c сообщением *«runtime canceled this request because it detected that your Worker's code had hung»* и `event.rpcMethod="run"` (`evidence-tail.jsonl`). Это отмена заблокированного вызова `run()` при уходе в hibernation, а не сбой задачи: Task Store тем временем в `awaiting_input`, после сигнала всё дорабатывает. Reporting-статусы читаем из Task Store (INV-20) — и это ещё одно подтверждение, что статус движка врёт.

### (в) Деплой во время ожидания

Сценарий: задача в `awaiting_input` (версия кода **v1** записана в `mark-awaiting`) → `wrangler deploy` с маркером **v2** (файл `src/version.ts`, переписывается и восстанавливается автоматически) → задача после деплоя осталась `awaiting_input`, не упала → через 60 с `POST /signal` → дошла до `done`.

Ключевое доказательство финального прогона из `evidence-d1-status.json` (одним SQL к удалённой D1):

### Диагностика #91 и #92 (замеры 02.10.2026, `cloud/deploy-wake-probe.sh`)

Матрица: задача в `awaiting_input` → `wrangler deploy` (маркер v(N) → v(N+1)) → сигнал через 2 или 5 с после возврата команды, варианты `prewarm` (вызов в инстанс до отправки события) и повторная отправка через 10 с. Сигнал несёт `expectVersion` — guard из #92.

| итерация | задержка | prewarm | повтор | status | код на пробуждении | вход в wait → пробуждение |
|---|---|---|---|---|---|---|
| p1 | 5 с | да | нет | `failed version_mismatch` (expected v2, **actual v1**) | **старый** | **61 мс** от сигнала |
| p2 | 5 с | нет | нет | `awaiting_input` — событие **не доставлено** (>30 мин) | — | — |
| p3 | 5 с | да | да | `done`, apply **v4** | новый | **300 281 мс** |
| p4 | 5 с | нет | да | `done`, apply **v5** | новый | **300 249 мс** |
| p5 | 2 с | да | да | `failed version_mismatch` (expected v6, **actual v5**) | **старый** | **68 мс** от сигнала |
| p6 | 2 с | нет | нет | `failed version_mismatch` (expected v7, **actual v1**) | новый (после финального restore-деплоя) | **300 202 мс** |

Что это значит:

1. **Задержка не в нашем пути запроса.** `prewarmMs` 5–18 мс, `sendMs` 40–62 мс, `deliveryMs` ≤377 мс — событие принято мгновенно. В `wrangler tail` три независимых заблокированных `run()` отменены платформой с `wall = 300 384 / 300 391 / 300 412 мс` (`outcome=canceled`): платформа отменяет зависшую инвокацию `run()` ровно через **300 с** после входа в `waitForEvent` и вызывает её заново — уже на новом коде. Ровно эта отмена и есть пробуждение в медленных случаях (279–285 с от сигнала = 300 с от входа в ожидание минус время, которое задача уже ждала).
2. **Середины нет: либо ~65 мс, либо 300 с.** Быстрое пробуждение означает, что событие досталось ещё **не заменённому** инстансу → он выполнил **старый** код → guard `expectVersion` честно валит задачу с `version_mismatch`. Медленное (300 с) означает, что инстанс был заменён → на новом коде → задача доходит корректно.
3. **Prewarm и повторная отправка не спасают** от300-секундного пути: p3 (prewarm+повтор) и p4 (повтор) — 279–280 с; p1/p5 (prewarm, без деплоя инстанса к моменту сигнала) — 61/68 мс. Повторная отправка события через 10 с не ускоряет ничего — событие и так принято и лежит в очереди.
4. **Пропагация версии замерена (#92):** edge (`GET /version`) отдаёт новый маркер через **165–286 мс** (первый замер после включения tail — 4415 мс); **новая** задача, созданная через **5 с** после деплоя, пошла на старом коде (p6: ждала на v5 при развёрнутом v6), через **6 с** — уже на новом (p2: v2). Ожидающий инстанс при сигнале через 2–5 с после деплоя — старый код (p1, p5), при пробуждении после 300-секундного окна — новый (p3, p4, p6).
5. **1 из6 — событие не доставлено дольше 30 минут** (p2) — та же недетерминированность, что и `wait_timeout` в issue #90: наблюдение вокруг деплоя, воспроизводится не всегда.

**Решение (перенесено в [COMPARISON.md](COMPARISON.md) → «Облачная проверка», с цифрами до/после):**

- деплоить **в паузах** — когда нет задач в `awaiting_input`: без деплоя пробуждение стабильно 180–641 мс;
- если деплой уже случился — **SLO пробуждения 300 с** для сигналов, пришедших в это окно, и **не ретраить** сигнал (замерено: ретраи не ускоряют);
- логику шагов менять только **additive**-деплоями; guard `expectVersion` гарантирует, что старый код никогда не молча не выполнит новую логику — control plane получает явный `version_mismatch` и пересоздаёт задачу (новый инстанс гарантированно на новом коде).

Два вывода, оформлены в issues:

1. **Пробуждение сразу после деплоя непредсказуемо по латентности** (61 мс … 270 с, теперь с механизмом: отмена заблокированной инвокации `run()` через 300 с) — issue [#91](https://github.com/trained-assist/trained-agent-architecture/issues/91). Без деплоя на тех же задачах 180–641 мс стабильно.
2. **Новый код до инстансов доезжает с задержкой ≥5–6 с после возврата `wrangler deploy`** (p6 проснулся через 2 с и выполнил старый код; guard это зафиксировал) — issue [#92](https://github.com/trained-assist/trained-agent-architecture/issues/92). Практическое следствие: если деплой содержит смену логики, полагаться на новый код у ожидающих экземпляров можно только после окна пропагации; имена/порядок шагов менять нельзя в любом случае.

## Найденный баг (блокер контракта Task Store, не выбора площадки)

Один раз у **уже завершённого** экземпляра (`done` в 18:13:12Z) через 3 мин 48 с в `task_events` пришло позднее `wait_timeout`, и статус в `tasks` перезаписался `done → failed` при том же `generation=1`. Движок (`instances describe --json`: `status=complete`, все шаги Success, error=null) об этом «не знает» — запись появилась только в D1. Повторно не воспроизводилось (**0 перезаписей у 10 следующих завершений**) → issue [#90](https://github.com/trained-assist/trained-agent-architecture/issues/90).

Вывод для A2/B1: **generation-фенсинга недостаточно** — терминальные статусы (`done/failed/cancelled`) обязаны быть неизменяемыми (guard в `commitStep`), и `catch` тайм-аута не должен писать `failed` поверх `done`. На выбор движка это не влияет: это наш слой Task Store.

**Исправлено 02.10.2026 (см. PR к #90):**

- `commitStep` получил второй фенс `status NOT IN ('done','failed','cancelled')` на UPDATE статуса, INSERT истории и INSERT счётчика (порядок в batch: история/счётчики до UPDATE, иначе `finalize` потерял бы собственную строку истории). Поздняя запись бросает `TerminalStateError` и оставляет только аудит-строку `late_write_rejected`/`wait_timeout_ignored`.
- `catch` вокруг `step.waitForEvent` различает дедлайн (`isWaitTimeoutError`, `WorkflowTimeoutError` / `Execution timed out after Nms`) и любую другую ошибку: `wait_timeout`/`user_reply_timeout` против `wait_error`/`wait_error`.
- **Воспроизводимый тест:** локальный T9 (`./run.sh`) — запись `wait_timeout` и статусная запись с текущим generation в уже `done`-задачу ничего не меняют (0 строк `wait_timeout`, 2 аудит-строки), 9/9 PASS.
- **Облачная репродукция (C4 в `cloud-run.sh`):** три `wrangler deploy` (маркеры v3/v4/v5, код шагов не менялся) в окне3 минут после `done` задачи C3 → `changed=false`, `wait_timeout_after_finalize=0`, `late_writes=0` (run 064632). Сам триггер из issue по-прежнему не детерминирован —0 перезаписей, как и раньше; но теперь перезапись невозможна на уровне схемы.

## Вердикт A1

**Control plane на Cloudflare годится — выбираем Cloudflare Workflows + D1.** Все три условия из COMPARISON.md пройдены на реальном аккаунте с доказательствами в `cloud/evidence-*`. Запасной вариант DBOS + Postgres на VM остаётся запасным (не нужен по итогу A1).

Условия принятия решения, которые вытекают из прогона (не меняют выбор площадки, но обязательны к учёту в M1/A2):

1. **Терминальные статусы защищаются в Task Store** — issue [#90](https://github.com/trained-assist/trained-agent-architecture/issues/90) (generation-фенсинга одного недостаточно). **Закрыто 02.10.2026:** guard в `commitStep` + классификация ошибки ожидания, локальный тест T9 (9/9) и облачная репродукция C4 (3 деплоя после `done` → 0 перезаписей).
2. **Деплой во время активного ожидания допустим** (экземпляры выживают), но пробуждение после деплоя — гонка с двумя исходами: ~65 мс на старом коде либо ровно 300 с на новом — issue [#91](https://github.com/trained-assist/trained-agent-architecture/issues/91). **Решение:** деплоить в паузах (нет `awaiting_input`), иначе SLO пробуждения 300 с и без ретраев; полный механизм и цифры — раздел «Диагностика #91 и #92».
3. **Новый код до ожидающих инстансов доезжает ≥5–6 с после возврата `wrangler deploy`** (через 5 с — старый, через 6 с — новый) — issue [#92](https://github.com/trained-assist/trained-agent-architecture/issues/92). **Закрыто 02.10.2026:** guard `expectVersion` в сигнале → явный `version_mismatch` вместо тихого результата со старой логикой (3 из6 итераций пойманы); контроль — additive-деплои, а по `version_mismatch` control plane пересоздаёт задачу.
4. **Шаги держать лёгкими** (CPU 4–10 мс/инвокацию на Free) либо закладывать Workers Paid; тяжёлые side effects — через D1/очереди с идемпотентностью по `(userTaskId, шаг)`. Тяжёлые артефакты (вместо лимита «результат шага 1 МиБ») — в **персональный GCS-бакет юзера**, в Task Store только ссылка/хэш/размер.
5. Регион D1 (EEUR) и юридические ограничения региона хранения — сверить с требованиями владельца до прод-миграции (по COMPARISON.md это единственное, что могло бы сместить решение в DBOS).
