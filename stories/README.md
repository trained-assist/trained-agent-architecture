# Истории — что система даёт людям и программам

Канонический источник пользовательских историй новой системы. **Фокус (решение владельца 30.09): основные запросы любого пользователя; доменная работа — потом ([LATER](LATER.md)).** Истории описывают **ценность и шаги**, не привязываясь к текущей реализации; на них опираются архитектура, контракты, карточки [плана](../IMPLEMENTATION-AND-INTEGRATION-PLAN.md) и приёмка.

| Файл | Для кого | Истории |
|---|---|---|
| [USER](USER.md) | человек в Telegram / Web | U-01…U-33 |
| [API](API.md) | программа по ключу: наши тесты, интегратор, другой агент, шлюзы | API-01…API-16 |
| [OPERATOR](OPERATOR.md) | оператор, владелец, разработчик | DEV-01…02, OPS-01…11 |
| [FAST-REPLIES](FAST-REPLIES.md) | проверка | диалоги, на которые отвечает код или одна модель, а не агент; корпус FR-001… |
| [PROBES](PROBES.md) | проверка | сценарии-ловушки из настоящих сбоев, PR-01… |

Формат каждой истории: **кто → ценность → шаги → «готово, когда» → этап плана.** «Готово, когда» — только то, что видно снаружи (пользователю, клиенту API, в журнале). Механизмы и имена компонентов сюда не пишутся.

## Пробелы плана

Истории, для которых в плане нет карточки или карточка покрывает их частично. Это вопросы к плану, а не к историям; решение — отдельной правкой плана.

**Человек**
- U-12 — явный выбор при новой задаче во время идущей (решение владельца 30.09, [RC](../scenarios/interaction/run-conflict-explicit-choice.md)). Рекомендация: добавить в приёмку P12 (модель) и P10/P11 (канал).
- U-13 — передать данные работающей задаче. Для API есть только повтор с инструкциями (P06).
- U-15 — разные чаты и вкладки параллельно; ожидание ресурса видно.
- U-19 — ожидание ответа пользователя как общий механизм (в плане только Web-вид в P21).
- U-20 — честный отказ по бюджету/моделям.
- U-21 — видимость фоновой работы (одно статус-сообщение, итог, стоп в статусе).
- U-31 — журнал и сводка «что делал агент».

**API-клиент** (в спецификации API нет):
- операция «дай журнал» с уровнями (API-04), ответ на вопрос агента (API-08), дополнение (API-09);
- подпись и регистрация адреса уведомлений (API-10), список задач (API-11), формат отказов (API-12), расход и лимиты (API-13), ключи (API-14), тестовый режим (API-15);
- единый набор состояний: сейчас состояния API, модель статусов Reporting и типы событий в контрактах не сведены; «cancel» и «stop» названы по-разному.

**Оператор/владелец:** служебный вид по номеру задачи (OPS-04), отчёт о расходах (OPS-07), закрепление модели (OPS-08), перенос данных (OPS-10).

**Домены:** вне фокуса ([LATER](LATER.md)); в плане остаётся пилот P26.

**Предпосылки без карточек:** пилот P-DB в облаке, схема хранилища задач, контракт «разговор / проект / аудитория» — от них зависят P12 и P22.

## Открытые вопросы по первому сценарию (U-02)

В плане и архитектуре не зафиксировано:
1. **Что перезапускается** между 3-й и 4-й репликой: исполнитель, управляющий слой или оба. Рекомендация: оба по очереди, двумя прогонами — иначе проверка не покрывает потерю состояния в управляющем слое.
2. **Текст пяти реплик и проверка «контекст сохранён».** Рекомендация: фиксированный сценарий, где 4-я и 5-я реплики требуют факт из 1-й, проверка — по содержанию ответа.
3. **Пороги задержки и стоимости.** Сейчас только «записать рядом со старым прод-путём». Рекомендация: порог «не хуже старого пути +20%» как гейт перевода пилота, а не первого прогона.

## Правила ведения

1. Новая или изменённая история — только здесь, в `stories/`. `scenarios/sources/` — неизменяемый снапшот старых репозиториев.
2. История — ценность и шаги. Механизм, код, инцидент, статус реализации — в контракты, архитектуру, issues.
3. Карточка плана и issue ссылаются на ID историй, которые закрывают. История, у которой нет этапа, помечается ⚠ и попадает в «Пробелы плана».
4. Решение владельца, меняющее поведение, записывается в историю с датой.
5. ID не переиспользуются. Удалённая история помечается «снята: причина».
