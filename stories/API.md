# Истории API-клиента

**Кто это:** программа, которая запускает агента по ключу: наши собственные тесты, внешний интегратор, другой агент, Error Watcher; Web и Telegram-шлюз — тоже клиенты этого API. Именно API-клиент — первый «пользователь» новой системы: по плану он получает работающую систему раньше человека (I02A), поэтому его истории — самые ранние.

Формат тот же: кто → ценность → шаги → «готово, когда» → этап. Имена полей и транспорт (HTTP, поток событий) здесь не фиксируются — это [Serverless Agent API](../SERVERLESS-AGENT-API.md) и [контракты](../contracts/README.md). Истории задают, **что** клиент должен уметь; ⚠ — поведение, которого в спецификациях пока нет.

---

## А. Запустить и наблюдать — первый срез API

### API-01. Запустить агента и получить квитанцию

**Ценность:** одной командой по ключу отдаю задачу и сразу получаю номер, по которому потом всё найду.

1. Отправляю задачу: текст, ссылки на входные файлы, желаемые ограничения (время, бюджет), куда отдавать результат.
2. Получаю квитанцию: номер задачи, время приёма, где смотреть статус.
3. Отправляю то же самое ещё раз (сеть моргнула) — получаю ту же квитанцию, вторая задача не создаётся.

**Готово, когда:** квитанция означает «принято и не потеряется», а не «запущено» или «готово»; повтор с тем же ключом повтора — та же квитанция, с другим содержимым — конфликт; без права — отказ до запуска.
**Этап:** I02A · P04.

### API-02. Следить за статусом и событиями

**Ценность:** в любой момент знаю, что происходит с задачей, и не теряю итог при обрыве связи.

1. Спрашиваю статус по номеру: в очереди / запускается / работает / ждёт ответа / завершается / успех / ошибка / отменена.
2. Подписываюсь на поток событий.
3. Связь оборвалась — переподключаюсь с последнего полученного события и получаю пропущенное.

**Готово, когда:** состояния различимы; разрыв потока не теряет итог; «связь с исполнителем потеряна» — отдельное состояние, а не ошибка; статус не запускает агента и ничего не стоит.
**Этап:** I02A · P05.

### API-03. Остановить задачу

**Ценность:** могу прервать ненужную работу и точно знать, остановлена ли она.

1. Отправляю «отмена» по номеру.
2. Получаю «запрос принят».
3. Отдельно получаю «остановлено» — когда это подтверждено.

**Готово, когда:** «запрос принят» не выдаётся за «остановлено»; отмена действует только на эту задачу; после отмены задача не перезапускается сама.
**Этап:** I02A · P05 (исполнитель — P02).

### API-04. Получить результат и журнал

**Ценность:** забираю не только ответ, но и всё, чтобы разобраться, что делал агент и почему упал. Для наших тестов это главный инструмент отладки.

1. Задача завершилась — забираю итог: результат, список файлов, ошибки выгрузки.
2. Забираю журнал задачи по уровням:
   - события жизненного цикла (принято, запущено, шаг, завершено) — всегда;
   - ошибки в структурированном виде: код, безопасное описание, можно ли повторить — всегда;
   - полный журнал агента (что он вызывал и отвечал) — если включён для этого ключа/задачи.
3. Всё доступно в течение объявленного срока хранения.

**Готово, когда:** журнал доступен только владельцу задачи; секреты и чужие данные в журнал не попадают; «успех» не выдаётся до сохранения результата; ошибка выгрузки видна отдельно от исхода работы.
**Этап:** события и ошибки — I01 · P02 + I02A · P05; ⚠ **операции «дай журнал» в спецификации API нет** — сейчас там только «доступные logs» внутри результата.

### API-05. Задача переживает перезапуск, повтор — по моему сигналу

**Ценность:** принятая задача не пропадает при сбое сервиса, и я сам решаю, запускать ли её снова.

1. Сервис перезапустился — задача на месте, статус честный: доделана / неизвестно / отменена.
2. Отправляю «повторить» по номеру, при желании с дополнительными инструкциями.
3. Номер задачи сохраняется, появляется новая попытка.

**Готово, когда:** после перезапуска принятая задача не исчезает и не запускается дважды; повтор сигнала не создаёт двух попыток; всё проходит без Telegram и Web.
**Этап:** I02A · P06.

## Б. Файлы

### API-06. Передать входные файлы и забрать выходные

**Ценность:** гоняю файлы любого размера напрямую, не через тело запроса.

1. Прошу место для загрузки — получаю временную ссылку.
2. Загружаю файл (большой — частями, с продолжением после обрыва).
3. Ссылаюсь на файл в задаче.
4. После задачи получаю список файлов результата и временные ссылки на скачивание.

**Готово, когда:** скачанные байты совпадают с созданными; просроченная или чужая ссылка не работает; неудачная выгрузка не удаляет единственную копию.
**Этап:** I02B · P07–P08.

### API-07. Рабочая папка между попытками

**Ценность:** следующая попытка видит файлы предыдущей; два писателя не затирают друг друга молча.

1. Запускаю задачу с рабочей папкой.
2. Следующая попытка видит прежние файлы.
3. Конфликт версий — явная ошибка, а не тихая перезапись.

**Готово, когда:** работают оба режима — «без профиля» и «с папкой»; выход за пределы папки отвергается.
**Этап:** I02B · P09.

## В. Диалог с работающей задачей

### API-08. Ответить на вопрос агента

**Ценность:** агент может спросить (логин, выбор) — я отвечаю программно, и работа продолжается.

1. Статус: «ждёт ответа», с номером вопроса и текстом.
2. Отправляю ответ на этот номер.
3. Работа продолжается той же задачей; повторный ответ не засчитывается дважды.

**Готово, когда:** ожидание не держит агента бесконечно; истечение ожидания даёт явный исход.
**Этап:** ⚠ в спецификации API операции ответа нет (принцип — есть; для Web — P21).

### API-09. Дополнить работающую задачу

**Ценность:** передаю уточнение, не останавливая работу, и знаю, куда оно попало.

1. Отправляю дополнение по номеру задачи.
2. Получаю ответ: принято в текущую работу / в следующую попытку / как новая задача.

**Готово, когда:** вариант указан явно в ответе.
**Этап:** ⚠ описано только в контрактах (C03), в API нет.

## Г. Эксплуатация клиента

### API-10. Получать события на свой адрес

**Ценность:** не опрашиваю статус — система сама сообщает о событиях.

1. Указываю адрес для уведомлений при запуске.
2. Получаю события с подписью, по которой проверяю подлинность.
3. Мой сервер недоступен — система повторяет ограниченное число раз, и это видно в статусе доставки.

**Готово, когда:** у каждого события есть номер для отсева дублей; ⚠ подпись, регистрация адреса и расписание повторов не описаны.
**Этап:** I02A (логика есть в спецификации); ⚠ карточки нет.

### API-11. Список моих задач

**Ценность:** нахожу свои задачи без хранения всех номеров: по времени, статусу, метке.

1. Запрашиваю список с фильтрами.
2. Получаю краткие карточки со ссылками на статус.

**Готово, когда:** в списке только задачи этого ключа/владельца.
**Этап:** ⚠ не описано.

### API-12. Понятные отказы

**Ценность:** по ответу понимаю, что исправить: ключ, лимит, регион, размер, недоступный движок, частота запросов.

1. Отправляю неправильный запрос.
2. Получаю код причины, понятное описание и когда можно повторить.

**Готово, когда:** у каждого отказа при приёме — свой код; «нет доступа к сервису», «лимит», «сервис недоступен» различаются.
**Этап:** ⚠ формат ошибок ответа API не описан (есть только формат журнала ошибок).

### API-13. Стоимость и лимиты

**Ценность:** знаю, сколько стоила задача и сколько бюджета осталось.

1. В итоге задачи вижу расход (модели, время исполнителя).
2. Запрашиваю остаток лимита по ключу.
3. Лимит кончился — отказ с понятной причиной до запуска, а не посреди работы.

**Готово, когда:** неизвестный расход не показывается нулём; дорогая модель не включается сама.
**Этап:** ⚠ правила есть (Model Gateway), операции для клиента нет.

### API-14. Ключи

**Ценность:** выпускаю, ограничиваю и отзываю ключи сам.

1. Получаю ключ с набором прав (движки, инструменты, регион, лимиты).
2. Отзываю ключ — задачи по нему больше не принимаются.

**Готово, когда:** ключ даёт доступ только к своим задачам и данным.
**Этап:** ⚠ выдача, ротация и отзыв не описаны.

### API-15. Тестовый режим

**Ценность:** гоняю свои тесты интеграции дёшево и детерминированно, без настоящего агента.

1. Запускаю задачу в тестовом режиме.
2. Получаю предсказуемый результат и события по заданному сценарию, включая сбои.

**Готово, когда:** тестовый режим не тратит бюджет моделей и явно помечен в итоге.
**Этап:** ⚠ сейчас есть только внутренний поддельный исполнитель; для клиента не описан.
